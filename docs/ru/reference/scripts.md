# Скрипты

[English](../../en/reference/scripts.md)

На этой странице перечислены все скрипты Python скиллов `specadoc` и
`orchestrator`: назначение, подкоманды, флаги и коды выхода. Флаги взяты из
вывода `--help` и кода argparse. `tests/test_docs.py` проверяет, что у каждого
скрипта здесь есть раздел.

## Обозначения

- `<skill-root>` — установленная папка `skills/specadoc`. В Claude Code это
  `${CLAUDE_SKILL_DIR}`.
- `<orchestrator-root>` — установленная папка `skills/orchestrator`.
- Запускайте каждую команду из корня репозитория. Скрипты отсчитывают
  относительные пути от текущего каталога.
- `<root>` — корень артефактов. См. [Определение корня артефактов](#определение-корня-артефактов).
- Если хост требует префикс или обёртку для команд, добавьте их к каждой команде.

## Версия Python

Скрипты используют только стандартную библиотеку Python. Каждый скрипт
жизненного цикла сначала импортирует `specadoc_config.py`. Этот модуль
останавливает скрипт с кодом выхода 2, если версия Python ниже 3.10. Для
файлов ролей Codex (TOML) нужен Python 3.11 или новее.

Минимальная поддерживаемая версия — Python 3.10. Проверкам мейнтейнера в
`scripts/check.sh` нужен Python 3.11 или новее.

Флаги рантайма (`--controller-runtime`) принимают `claude`, `codex` и
`opencode`. Также они принимают `claude-code` как псевдоним `claude`.

## Определение корня артефактов

Каждый скрипт, который читает или пишет артефакты, определяет корень в таком
порядке. Действует первое совпадение.

1. Флаг `--root <path>`.
2. Переменная окружения `SPECADOC_ROOT`.
3. Ключ `root` файла `.specadoc.json` в текущем каталоге.
4. Устаревший корень `docs/agent`, если он есть, а `docs/specadoc` нет.
5. Корень по умолчанию `docs/specadoc`.

Для устаревшего корня скрипт выводит предупреждение в stderr. Чтобы перенести
корень, запустите [`migrate_root.py`](#migrate_rootpy). `doctor.py` и
`init_change.py` выводят определённый корень и его источник (`cli`, `env`,
`config`, `legacy` или `default`).

## archive_change.py

Проверяет изменение и сжимает его в одну неизменяемую архивную запись
`record.md`. См. [archive](modes.md#archive).

```text
python3 <skill-root>/scripts/archive_change.py [--root ROOT] [--dry-run] [--force] change_slug
```

| Флаг | Значение |
|---|---|
| `change_slug` | Слаг изменения. |
| `--root ROOT` | Корень артефактов. По умолчанию определяется автоматически. |
| `--dry-run` | Выполняет все проверки и выводит результат. Ничего не записывает. |
| `--force` | Сжимает изменение, даже если гейты не пройдены. Архивная запись перечисляет непройденные гейты. |

Скрипт отказывается архивировать изменение, если выполнено одно из условий:

- открыт гейт жизненного цикла, или результат ревью не PASS
- `review_snapshot.py verify` находит отличия после последнего PASS
- нет объявленной спецификации возможности
- в спецификации возможности нет строки происхождения для слага
- id из `ADDED`, `MODIFIED` или `RENAMED` нет в спецификации возможности, или
  id из `REMOVED` всё ещё есть в ней
- в папке изменения есть неизвестное вложение
- `<root>/archive/<slug>/` уже существует
- архивная запись больше 16 KiB.

`--force` обходит гейты жизненного цикла и происхождения. Флаг никогда не
перезаписывает цель и никогда не пропускает проверку архивной записи. Скрипт
удаляет папку изменения только после того, как прочитает запись обратно. Файлы
в `runs/` не считаются неизвестными вложениями. Они становятся одной строкой
манифеста источников.

Коды выхода: 0 успех, 1 ошибка архивации (причина в stderr), 2 корень не
удалось определить.

## collect_tokens.py

Суммирует счётчики токенов всех исполнений одного изменения. Исполнение — один
запуск: транскрипт контроллера или один дочерний агент.

```text
python3 <skill-root>/scripts/collect_tokens.py change_slug [sources ...] --harness {claude,codex,opencode}
    --mode {explore,light,propose,apply,archive} [--directory DIR] [--db DB] [--session ID]
    [--external-run RUN_JSON] [--final | --provisional] [--root ROOT] [--project DIR] [--append]
```

| Флаг | Значение |
|---|---|
| `sources` | Транскрипты или папки, для `claude` и `codex`. |
| `--harness` | Харнесс, который записал транскрипты. Обязательный. |
| `--mode` | Режим Specadoc этих исполнений. Обязательный. |
| `--directory DIR` | OpenCode: путь к репозиторию, в котором шла сессия. |
| `--db DB` | OpenCode: расположение базы данных. |
| `--session ID`, `--root-session ID` | OpenCode: включает эту сессию и её потомков. Для возобновлённых корневых сессий повторите флаг. |
| `--external-run RUN_JSON` | Запись завершённого запуска `run_role.py`. Повторите флаг для каждого внешнего исполнения. |
| `--final` | Помечает сбор как окончательный. |
| `--provisional` | Помечает сбор как предварительный. Это значение по умолчанию. |
| `--root ROOT` | Корень артефактов. По умолчанию определяется автоматически. |
| `--project DIR` | Предупреждает об исполнениях, которые записаны вне этой папки. |
| `--append` | Записывает итоги в `plan.md`, а строки в `runs/tokens.md`. |

В каждой строке два числа. `unique` — некешированный ввод плюс запись в кеш плюс
вывод. `read` — кешированный ввод. Эти числа показывают объём контекста, а не
счёт провайдера. Не сравнивайте их между харнессами.

Если путь к источнику не задан, бэкенд `claude` берёт сессии, которые
`specadoc_step.py` записал в `runs/sessions.json`. Если этого файла нет, бэкенд
берёт самую новую сессию проекта и сообщает, какую именно.

`--append` заменяет только записи этого режима и харнесса. Остальные записи
остаются.

Коды выхода: 0 успех, 1 нет ни одного исполнения со счётчиком токенов, 2
`--final` с предупреждениями о пропущенных, неполных входных данных или данных
без области, или корень не удалось определить.

## doctor.py

Сообщает о нарушениях целостности спецификаций возможностей и архивных
записей. С флагом `--probe` проверяет оболочку, в которой работает сессия.
Команда только читает файлы.

```text
python3 <skill-root>/scripts/doctor.py [--root ROOT] [--strict]
    [--controller-runtime {claude,codex,opencode}] [--probe] [--expect-head SHA] [--baseline]
```

| Флаг | Значение |
|---|---|
| `--root ROOT` | Корень артефактов. По умолчанию определяется автоматически. |
| `--strict` | Возвращает ненулевой код и при предупреждениях. |
| `--controller-runtime` | Также проверяет маршрутизацию ролей, наличие CLI и независимость reviewer. |
| `--probe` | Проверяет среду запуска вместо спецификаций. |
| `--expect-head SHA` | С `--probe`: ревизия, на которой работает родительская сессия. |
| `--baseline` | С `--probe`: также запускает каждую команду `verification.final` на рабочей копии. |

Без `--probe` doctor сообщает о таких проблемах:

- повторяющиеся id `C<n>`
- повторяющиеся строки происхождения
- точные дубликаты текста требований в разных спецификациях возможностей
- повторяющиеся слаги архивов
- ссылки архива, которые больше не ведут к спецификации возможности или к её
  происхождению
- ключевые пути, которых нет в репозитории.

doctor никогда не меняет артефакты. С `--controller-runtime` он считает
отсутствующий CLI рантайма ошибкой. Если `worker` и `reviewer` используют один
рантайм, doctor выводит одно предупреждение.

С `--probe` doctor проверяет:

- исполняемые файлы `verification.final` и интерпретатор из их строки `#!`
- CLI и доступную для записи домашнюю папку каждого рантайма из маршрутизации
- рабочую копию, а также ревизию, если задан `--expect-head`
- каждую команду `verification.probe` (код 0 за 60 секунд).

Коды выхода без `--probe`: 0 ошибок нет, 1 есть ошибки (или предупреждения с
`--strict`), 2 корень не удалось определить. С `--probe`: 0 PASS, 1 ошибка.
`--expect-head` или `--baseline` без `--probe` дают код выхода 2.

## init_change.py

Создаёт `spec.md` и `plan.md` изменения по шаблонам из
`<skill-root>/assets/`.

```text
python3 <skill-root>/scripts/init_change.py change_slug [--root ROOT] [--risk {low,medium,high}]
    [--with-design] [--with-research] [--force] (--scout REF | --no-scout REASON)
```

| Флаг | Значение |
|---|---|
| `change_slug` | Имя изменения. Скрипт переводит его в kebab-case. |
| `--root ROOT` | Корень артефактов. По умолчанию определяется автоматически. |
| `--risk` | Риск, который скрипт записывает в шапки файлов. |
| `--with-design` | Также создаёт `design.md`. |
| `--with-research` | Также создаёт `research.md`. |
| `--force` | Перезаписывает существующие файлы. |
| `--scout REF` | Отчёт scout или id агента, который составил карту кода. |
| `--no-scout REASON` | Почему scout не запускали, например повторно использованы доказательства из explore. |

Укажите `--scout` или `--no-scout`. Скрипт заполняет в шапках поля названия,
риска, даты и scout.

Коды выхода: 0 успех, 1 ошибка файла (например, файл уже существует, а
`--force` не задан), 2 недопустимый слаг, пустое значение scout или корень не
удалось определить.

## list_changes.py

Выводит объект `status --json` каждого активного изменения за один вызов,
который только читает файлы. Его может использовать дашборд или скрипт
автоматизации.

```text
python3 <skill-root>/scripts/list_changes.py [--root ROOT]
```

Вывод — один объект JSON: `{root, active: [<status object> + updated_at], archived: N}`.
Активное изменение — папка в корне с файлом `plan.md`. Папки `archive/`,
`specs/` и `contracts/` не считаются изменениями. Если status изменения
завершился ошибкой, у изменения стоит `result: "error"`. Скрипт не читает
транскрипт контроллера, поэтому `context.tokens` равно 0.

Код выхода: 0.

## migrate_archive.py

Сжимает устаревшие папки архива в файлы `record.md`. Без `--apply` ничего не
записывает.

```text
python3 <skill-root>/scripts/migrate_archive.py [--root ROOT] [--apply] [--backup-root DIR]
```

| Флаг | Значение |
|---|---|
| `--root ROOT` | Корень артефактов. По умолчанию определяется автоматически. |
| `--apply` | Выполняет миграцию. |
| `--backup-root DIR` | Куда записать резервную копию. По умолчанию: `<root>/.archive-backups`. |

Пробный прогон выводит опись, ожидаемый размер и предпросмотр каждой записи.
Каждому устаревшему файлу, кроме `spec.md` и `plan.md`, нужен
`migration-summary.md`, который написал человек. С `--apply` скрипт сначала
пишет резервную копию `.tar.gz` с меткой времени и проверяет её. Резервную
копию скрипт никогда не удаляет.

Коды выхода: 0 успех, 1 ошибка миграции, 2 корень не удалось определить.

## migrate_root.py

Переносит корень артефактов и переписывает ссылки на корень в перенесённых
файлах Markdown. Без `--apply` ничего не записывает.

```text
python3 <skill-root>/scripts/migrate_root.py [--from SOURCE] [--to TARGET] [--apply]
```

| Флаг | Значение |
|---|---|
| `--from SOURCE` | Текущий корень. По умолчанию: `docs/agent`. |
| `--to TARGET` | Новый корень. По умолчанию: `docs/specadoc`. |
| `--apply` | Переносит папку. |

В рабочем дереве git скрипт переносит папку командой `git mv`. Каждая
буквальная строка `<from>/` в перенесённых файлах Markdown становится `<to>/`.
Хеши в архивных записях остаются действительными, потому что они описывают
исходные артефакты на момент архивации.

Коды выхода: 0 успех, 1 ошибка миграции или git.

## review_snapshot.py

Вычисляет хеш содержимого области ревью и проверяет область одной задачи
worker. Коммит или ref git для этого не нужен.

```text
python3 <skill-root>/scripts/review_snapshot.py {compute,verify,diff,baseline,check-scope} change_slug
    [--task T<n>] [--root ROOT] [--stored MANIFEST] [--previous G<n>|MANIFEST]
```

| Действие | Значение |
|---|---|
| `compute` | Выводит снимок: `{hash, manifest}`. |
| `verify` | Сравнивает текущий снимок с `--stored`. Выводит `match` или различия. |
| `diff` | Выводит различия относительно `--previous` (id раунда `G<n>` или манифест). |
| `baseline` | Перед отправкой задачи записывает манифест всего рабочего дерева в `runs/T<n>-baseline.json`. |
| `check-scope` | Завершается с ошибкой, если файл изменился вне `Files:` задачи или внутри корня артефактов. |

| Флаг | Значение |
|---|---|
| `--task T<n>` | Задача, для `baseline` и `check-scope`. |
| `--root ROOT` | Корень артефактов. По умолчанию определяется автоматически. |
| `--stored MANIFEST` | Для `verify`: путь к файлу JSON или JSON в строке. |
| `--previous` | Для `diff`: id раунда или манифест. |

Снимок — отсортированный манифест `{path: sha256}` для каждого пути из
`## Review scope`. В нём также есть одна запись `spec.md#contract` для разделов
спецификации Requirements, Acceptance scenarios, Constraints и Affected
capabilities. Файлы из папки изменения в области ревью запрещены.

Второй `baseline` для той же задачи сохраняет первый базовый снимок. Повторная
попытка никогда его не заменяет.

Коды выхода:

- 0: успех или `match`.
- 1: несовпадение (`verify`) или нарушение области (`check-scope`).
- 2: область нельзя определить, не задан флаг или корень не удалось определить.

## role_routing.py

Определяет рантайм, модель и уровень усилий каждой роли. Агентов скрипт никогда не
запускает. См. [Конфигурация](config.md#как-определяется-привязка-роли).

```text
python3 <skill-root>/scripts/role_routing.py --controller-runtime {claude,codex,opencode}
    [--cwd DIR] [--role {scout,worker,reviewer}] [--change SLUG] [--root ROOT]
    [--dry-run] [--check-cli] [--compact]
```

| Флаг | Значение |
|---|---|
| `--controller-runtime` | Рантайм контроллера, который вызывает скрипт. Обязательный. |
| `--cwd DIR` | Корень репозитория. По умолчанию: текущий каталог. |
| `--role` | Определяет только одну роль. |
| `--change SLUG` | Проверяет только роли, которые использует этот план. Ошибки других ролей становятся предупреждениями. |
| `--root ROOT` | Корень артефактов для `--change`. По умолчанию определяется автоматически. |
| `--dry-run` | Только чтение. Команда в любом случае не запускает агентов. |
| `--check-cli` | Также проверяет, что CLI каждого рантайма есть в `PATH`. |
| `--compact` | Краткая сводка JSON без сведений об источниках. |

Вывод в JSON: `{routes, findings}`. План использует `reviewer`, а `worker` —
если у задачи есть `Owner: worker`. При одобрении плана покажите результат с
флагами `--change <slug> --dry-run --compact --check-cli`.

Коды выхода: 0 ошибок нет, 1 есть замечание уровня ERROR, 2 план не читается
или единственную запрошенную роль нельзя определить.

## run_role.py

Запускает роль Specadoc через CLI другого рантайма и собирает её результат.
Если рантайм роли отличается от рантайма контроллера, используйте этот скрипт.
См. [Конфигурация](config.md#настройки-внешнего-запуска) и
[`references/runners.md`](../../../skills/specadoc/references/runners.md).

```text
python3 <skill-root>/scripts/run_role.py start --role {scout,worker,reviewer} --prompt-file FILE --name NAME
    [--controller-runtime RT | --runtime RT --model MODEL [--effort EFFORT]]
    [--cwd DIR] [--out-dir DIR] [--dry-run] [--no-progress-timeout SECONDS]
python3 <skill-root>/scripts/run_role.py wait RUN_FILE [--timeout S] [--shell-budget S] [--follow]
    [--interval S] [--no-progress-timeout S]
python3 <skill-root>/scripts/run_role.py status RUN_FILE [--no-progress-timeout S]
python3 <skill-root>/scripts/run_role.py result RUN_FILE
python3 <skill-root>/scripts/run_role.py stop RUN_FILE
```

| Подкоманда | Значение |
|---|---|
| `start` | Запускает CLI в фоне и выводит файл запуска. |
| `wait` | Ждёт запуск не дольше `--timeout` секунд. |
| `status` | Показывает состояние running, completed, failed или no-progress с диагностикой. |
| `result` | Проверяет итоговый JSON по схеме роли и сохраняет его. |
| `stop` | Останавливает запуск. |

Флаги `start`:

| Флаг | Значение |
|---|---|
| `--role` | Роль. Обязательный. |
| `--controller-runtime` | Определяет роль по маршрутизации проекта и файлу целевой роли. |
| `--runtime`, `--model`, `--effort` | Явная привязка для проектов без маршрутизации. |
| `--prompt-file FILE` | Бриф или полный промпт отправки задачи. Обязательный. |
| `--name NAME` | Имя запуска, обычно id задачи. Обязательный. |
| `--cwd DIR` | Корень репозитория, в котором работает роль. По умолчанию: `.`. |
| `--out-dir DIR` | Куда записать файлы запуска. По умолчанию: папка файла промпта. |
| `--dry-run` | Выводит команду CLI. Не запускает её. |
| `--no-progress-timeout S` | Лимит тишины в потоке, в секундах. По умолчанию: 900. 0 отключает лимит. |

Флаги `wait`:

| Флаг | По умолчанию | Значение |
|---|---|---|
| `--timeout S` | 120 | Максимальное время ожидания в секундах. |
| `--shell-budget S` | 120 | Лимит времени оболочки у хоста. Ожидание заканчивается за несколько секунд до него. |
| `--follow` | выключен | Выводит строку прогресса каждые `--interval` секунд. |
| `--interval S` | 45 | Интервал строк прогресса. |
| `--no-progress-timeout S` | из запуска | Переопределяет лимит тишины в потоке. Роль никогда не останавливается автоматически. |

Файл промпта, `--out-dir` и файлы запуска считаются относительно `--cwd`.
Файлы запуска: `<name>.<role>.run.json`, `.log`, `.result.json` и файл с кодом
выхода. Если запустить то же имя с тем же промптом и привязкой, скрипт
использует существующий запуск. Если промпт или привязка отличаются, задайте
новое `--name`.

С `--controller-runtime` скрипт отклоняет явные флаги `--runtime`, `--model`
или `--effort`, которые противоречат определённой привязке.

Коды выхода:

| Код | Значение |
|---|---|
| 0 | Успех. Для `wait`: запуск завершился. |
| 1 | `wait`: неустранимая ошибка транспорта. `result`: CLI завершился с ошибкой, или JSON не соответствует схеме. |
| 2 | Ошибка, например нет файла промпта, нет CLI или имя запуска конфликтует. |
| 3 | `wait`: запуск ещё идёт, или прогресса не было. Это не сбой роли. |
| 4 | `start`: рантайм не может писать в свою домашнюю папку или журнал в этой оболочке (`sandboxed:`). |

## specadoc_step.py

Выполняет один шаг жизненного цикла и выводит компактный результат. Каждый шаг
использует логику `review_snapshot.py`, `task_brief.py` и `validate_change.py`.

```text
python3 <skill-root>/scripts/specadoc_step.py [--root ROOT] <step> <arguments>
```

`--root` ставится перед именем шага. Каждый шаг выводит пять полей:

```text
checked: <what ran>
result: PASS | FAIL | BLOCKED | ...
changed files: <paths or ->
blocking reason: <reason or ->
next: <the next allowed step>
```

| Результат | Код выхода |
|---|---|
| PASS, CHECKED, ACCEPTED, EXTERNAL-PENDING | 0 |
| FAIL | 1 |
| BLOCKED, NEEDS_DECISION, WAITING | 2 |

FAIL — замечание, которое вы можете исправить. BLOCKED означает, что шаг не
может выполнить оценку. Неожиданная ошибка шага даёт BLOCKED.

Каждый шаг принимает `--controller-runtime {codex,claude,opencode}`. Флаг
используют шаги `preflight`, `dispatch`, `wait`, `pre-review`, `design-brief`,
`design-review` и `status`. Остальные шаги принимают флаг и игнорируют его.

### Шаги propose

| Шаг | Аргументы и флаги | Значение |
|---|---|---|
| `design-brief` | `<slug> [--full] [--attempt-decision 'continue: <source>' \| 'accept: <source>']` | Пишет `runs/design-brief.md` для reviewer дизайна. `--full` запрашивает полное ревью после переработки дизайна. |
| `design-review` | `<slug> (--result-file FILE \| --from-agent ID) [--same-reviewer-reason TEXT]` | Записывает вердикт дизайна в `## Design review` с привязкой к хешу реестра классов. |
| `design-resolve` | `<slug> --file FILE\|-` | Отвечает на каждый пункт раунда дизайна с FAIL: `F1.2: resolved: <where>` или `F1.2: rejected: <why>`. |
| `approve` | `<slug> --by {user,orchestrator} --source TEXT [--bindings TEXT]` | Записывает одобрение плана и его источник. Записывает хеши `spec.md` и `design.md` в `runs/approval.json`. |

После четырёх раундов дизайна новый раунд после FAIL требует
`--attempt-decision`. `continue: <source>` разрешает ещё один раунд.
`accept: <source>` закрывает гейт, и каждый открытый пункт IMPORTANT становится
обязательством дизайна в `## Global constraints`. Пункт BLOCKER никогда не
принимается.

`approve` отказывает, если ревью дизайна не актуально, раунд ревью ожидает
результата или `validate_change.py --phase plan` завершается с ошибкой. Шаг
также отказывает, если строка привязок не записана, а `--bindings` не задан.

### Шаги apply: задачи

| Шаг | Аргументы и флаги | Значение |
|---|---|---|
| `status` | `<slug> [--context-tokens N] [--json]` | Выводит состояния задач, последнее ревью и следующий разрешённый шаг. `--json` выводит один объект с `next.kind`. |
| `preflight` | `<slug> T<n>` | Проверяет задачу и не меняет файлы. Команды Verification не запускает. |
| `dispatch` | `<slug> T<n> [--context-tokens N] [--reopen REASON]` | Выполняет preflight, затем пишет базовый снимок задачи и `runs/T<n>-brief.md`. |
| `wait` | `<slug> T<n>\|tidy [--timeout S] [--shell-budget S]` | Ждёт новый отчёт задачи с любым статусом или запись tidy. Тайм-аут по умолчанию: 540 секунд. |
| `report` | `<slug> T<n> --status STATUS --summary TEXT --red TEXT --green TEXT [--mutation TEXT] [--concern TEXT] [--body-file FILE]` | Пишет отчёт задачи и его JSON с результатом по фактическим изменениям. |
| `accept` | `<slug> T<n> [--scope-only] [--result-file FILE] [--note TEXT] [--resolved HOW] [--verification-timeout S]` | Проверяет область, проверяет отчёт, запускает команды Verification, снова проверяет область, записывает доказательства (Evidence). |
| `external-result` | `<slug> T<n> --outcome {PASS,FAIL} --evidence TEXT [--log PATH] [--supersede REASON]` | Записывает результат проверки `External verification:` задачи. |
| `amend` | `<slug> T<n> [--allow PATH] [--derived PATH] [--controller-path PATH] --reason TEXT` | Добавляет в область задачи путь worker, производный путь или правку контроллера. |
| `manifest` | `<slug> T<n>` | Выводит в JSON изменённые пути и предлагаемые пункты области ревью. |
| `refresh` | `<slug> [--verification-timeout S] [--controller-path PATH] [--reason TEXT]` | Заново принимает каждую закрытую задачу с устаревшими доказательствами, в порядке зависимостей. |
| `handoff` | `<slug> --file FILE\|-` | Перезаписывает `runs/handoff.md`. Не больше 4 KiB. |

Статусы `report`: `DONE`, `DONE_WITH_CONCERNS`, `NEEDS_CONTEXT` и `BLOCKED`.
Если тест не падал до написания кода, используйте `--mutation`. Укажите каждую
поломку, которую вы внесли, и тест, который после этого упал.

`dispatch` останавливается, когда наблюдаемый контекст контроллера приближается
к 200k токенов. Хосты, кроме Claude Code, передают `--context-tokens N`.
`--reopen REASON` начинает новую попытку более ранней задачи от текущего
дерева. Используйте этот флаг только для исправлений кода.

`accept` запускает поле Verification с правами вызывающего. Каждая команда в
поле должна стоять в обратных кавычках. Разделяйте команды точкой с запятой.
Значение `--verification-timeout` по умолчанию у `accept` и `refresh` — 600
секунд. `--resolved HOW` принимает отчёт BLOCKED или NEEDS_CONTEXT после того,
как блокер устранён.

`external-result --supersede REASON` заменяет записанный результат для того же
содержимого. Старый результат остаётся в `external_history`. FAIL возвращает
задачу в работу.

### Шаги apply: ревью и завершение

| Шаг | Аргументы и флаги | Значение |
|---|---|---|
| `scope` | `<slug> [--base REV] [--dry-run] [--exclude PATH]` | Заполняет `## Review scope` по diff от `--base` (по умолчанию `HEAD`) и добавляет неотслеживаемые файлы. |
| `tidy` | `<slug> [--record --summary TEXT [--from-agent ID] \| --skip REASON]` | Без флагов: пишет `runs/tidy-brief.md`. `--record`: записывает результат worker прохода tidy. `--skip`: записывает, почему проход не нужен. |
| `finalize` | `<slug> [--observed RUN] [--requirements WHY] [--run] [--timeout S] [--residual TEXT]` | Отмечает пункты Final verification, которые доказывает записанное состояние. Заполняет Completion evidence. |
| `pre-review` | `<slug> [--review-type {initial,re-review}] [--reason REASON] [--review-decision TEXT] [--dry-run] [--withdraw]` | Запускает гейт pre-review и записывает новый раунд `### G<n>`. Пишет `runs/G<n>-head.diff` и `runs/G<n>-status.txt`. |
| `review-result` | `<slug> (--result-file FILE \| --from-agent ID) [--same-reviewer-reason TEXT]` | Закрывает ожидающий раунд. Сохраняет ответ нативного reviewer в `runs/`. |

Флаги `finalize`:

- `--run` один раз запускает команды `verification.final` из `.specadoc.json`
  и записывает их в `runs/final-verification.json`. `--timeout` по умолчанию —
  1800 секунд на каждую команду.
- `--observed RUN` записывает полный набор тестов и гейты, которые запустил
  контроллер.
- `--requirements WHY` меняет каждый статус Pending в матрице на PASS и
  записывает доказательства одной строкой.
- `--residual TEXT` записывает остаточные риски или `none`.

Флаги `pre-review`:

- `--review-type` по умолчанию `initial`.
- `--reason`: `implementation`, `corrections`, `minor-fixes`, `requirements`
  или `polish`.
- `--review-decision` разрешает ограниченный дополнительный раунд. Укажите
  автора: слова пользователя или `orchestrator D<n> under mandate D<m>: <scope>`.
- `--dry-run` запускает гейт и выводит снимок. Раунд не записывает.
- `--withdraw` удаляет последний раунд, пока он в статусе Pending.

Четвёртый раунд `initial` требует `--review-decision`. Если в `.specadoc.json`
задано `review.tidy: required`, первому раунду `initial` нужна запись tidy.

`review-result` и `design-review` отклоняют агента reviewer из предыдущего
раунда. Чтобы разрешить его, задайте `--same-reviewer-reason`.

## task_brief.py

Пишет самодостаточный бриф одной задачи worker в
`<root>/<slug>/runs/T<n>-brief.md` и выводит путь. Скрипт вызывает `dispatch`.

```text
python3 <skill-root>/scripts/task_brief.py [--root ROOT] change_slug T<n>
```

Бриф содержит:

- блок задачи из `plan.md` дословно
- требования спецификации, которые называет задача
- сценарии приёмки, которые их покрывают
- раздел Constraints спецификации
- контракт сдачи работы: путь отчёта, схему результата и правила области
- `runs/lessons.md`, если файл есть; скрипт обрезает его до 2048 байт.

Если бриф больше 16 000 байт, скрипт выводит предупреждение и называет самые
большие части.

Коды выхода: 0 успех, 2 ошибка (причина в stderr).

## validate_change.py

Проверяет структуру `spec.md` и `plan.md` для одной фазы. Смысл скрипт
проверить не может. См. [Структура плана](plan-structure.md#что-проверяет-валидатор).

```text
python3 <skill-root>/scripts/validate_change.py change_slug --phase {spec,plan,pre-review,final}
    [--root ROOT] [--json] [--next-review-type {initial,re-review}] [--review-decision TEXT]
python3 <skill-root>/scripts/validate_change.py --files-hash "<Files: value>"
```

| Флаг | Значение |
|---|---|
| `--phase` | Контрольная точка для проверки. |
| `--root ROOT` | Корень артефактов. По умолчанию определяется автоматически. |
| `--json` | Выводит нарушения в JSON. |
| `--next-review-type` | Предлагаемая отправка на ревью. Не используйте флаг, чтобы сменить тип прошлого раунда. |
| `--review-decision TEXT` | Решение о предлагаемом дополнительном ревью и его автор. |
| `--files-hash FIELD` | Выводит хеш содержимого значения `Files:` задачи и завершает работу. |

| Фаза | Когда |
|---|---|
| `spec` | Перед техническим планированием. |
| `plan` | Перед предпросмотром плана. |
| `pre-review` | Перед отправкой задачи reviewer. |
| `final` | После PASS ревью и перед архивацией. |

Предупреждения идут в stderr и не меняют код выхода. Примеры: `plan.md` больше
48 KiB, больше восьми задач, команда `Verification`, которая начинается с
`NAME=value` или `env`.

Коды выхода: 0 нарушений нет, 1 есть нарушения, 2 нет папки изменения,
артефакта или аргумента, или корень не удалось определить.

## design_gate.py

Внутренний модуль. Читает `## Class inventory` плана и записывает независимое
ревью дизайна в `## Design review` с привязкой к хешу реестра классов.
`specadoc_step.py` использует модуль для `design-brief`, `design-review`,
`design-resolve`, `approve` и `dispatch`. Модуль хранит счётчик раундов в
`runs/design-round.json`. Лимит раундов — четыре.

## host_clock.py

Внутренний модуль. Обнаруживает спящий режим хоста во время ожидания. В macOS
монотонные часы во время сна останавливаются, а системные нет. `run_role.py wait`
и `specadoc_step.py wait` используют модуль, чтобы отличить спящий хост от
зависшей роли.

## mode_budget.py

Внутренний модуль. Сверяет размер текста скилла в байтах с
`<skill-root>/assets/mode-budget.json`. Файл сверх своего лимита — ошибка.
Режим сверх общего лимита — предупреждение. Модуль используют тесты
репозитория. См. [Структура плана](plan-structure.md#лимиты-размера).

## review_state.py

Внутренний модуль. Перед отправкой задачи reviewer вставляет раунд `### G<n>` в
`## Review result`, а потом закрывает результат. Модуль используют
`specadoc_step.py pre-review` и `review-result`. Модуль не даёт пометить
корректирующий раунд как `initial`.

## reviewer_reply.py

Внутренний модуль. Находит транскрипт нативного reviewer по id агента и
сохраняет итоговый ответ дословно в `runs/`. Это флаг `--from-agent` у
`review-result` и `design-review`. Модуль читает транскрипты в
`$CLAUDE_CONFIG_DIR/projects`, по умолчанию `~/.claude/projects`.

## specadoc_config.py

Внутренний модуль. Читает и проверяет `.specadoc.json` в текущем каталоге.
Также останавливает каждый скрипт с кодом выхода 2, если версия Python ниже
3.10. См. [Конфигурация](config.md).

## specadoc_root.py

Внутренний модуль. Определяет корень артефактов (см.
[Определение корня артефактов](#определение-корня-артефактов)). Также создаёт
папку `runs/` изменения с файлом `.gitignore`, который содержит `*`.

## task_state.py

Внутренний модуль. Хранит состояние задачи (схема `specadoc.task/v2`) в файле
базового снимка задачи `runs/T<n>-baseline.json`. Также проверяет одобрение
плана и готовность задачи перед отправкой.

## verification_inputs.py

Внутренний модуль. Вычисляет входные данные, от которых зависит, действительны
ли ещё принятые доказательства. Это Files и Derived files задачи, lock-файлы,
`Verification inputs` и дайджест каждой нужной переменной окружения. Значения
переменных модуль никогда не хранит. См.
[Конфигурация](config.md#verificationenvironment).

## ba_register.py

Команда оркестратора. Ведёт один нумерованный реестр: вопросы к
бизнес-аналитику, отклонения от источников и решения, которые приняли без аналитика.

```text
python3 <orchestrator-root>/scripts/ba_register.py add <file> --title T --step S --type T --status S
    [--section HEADING] [--file PATH|-]
python3 <orchestrator-root>/scripts/ba_register.py status <file> <n> --status S [--note TEXT]
python3 <orchestrator-root>/scripts/ba_register.py list <file> [--status TEXT]
```

| Подкоманда | Значение |
|---|---|
| `add` | Добавляет пункт со следующим номером. `--section` называет заголовок верхнего уровня `# `. По умолчанию: конец файла. |
| `status` | Меняет статус пункта `<n>` на месте. `--note` добавляет заметку с датой. |
| `list` | Выводит пункты, по желанию только с заданным статусом. |

Пункт — это `## <n>. <title> (<step>)` и одна строка с типом и статусом. Номер

## coordination_log.py

Команда оркестратора. Ведёт журнал нумерованных решений, в который только
добавляют записи, и один блок текущего состояния.

```text
python3 <orchestrator-root>/scripts/coordination_log.py decision <log> --by {user,orchestrator}
    --title TEXT --file PATH|- [--quote TEXT [--confirms TEXT]]
python3 <orchestrator-root>/scripts/coordination_log.py state <log> --file PATH|-
python3 <orchestrator-root>/scripts/coordination_log.py last <log>
python3 <orchestrator-root>/scripts/coordination_log.py get <log> D<n>
```

| Подкоманда | Значение |
|---|---|
| `decision` | Добавляет `### D<n> — <title> [by <author>] (<UTC time>)` после наибольшего D<n>. |
| `state` | Заменяет блок между маркерами текущего состояния. |
| `last` | Выводит заголовок самого нового решения. |
| `get` | Выводит одно решение. |

`--by user` требует `--quote` со словами самого пользователя. Ответ из одного
«go» или «ok» также требует `--confirms`: этот флаг называет единственное
принятое предложение. `--by orchestrator` — решение по мандату. Прежние записи
никогда не переписываются. Решение — не больше 2048 байт, блок состояния — не
больше 1536 байт.
