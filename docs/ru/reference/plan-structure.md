# Структура плана

[English](../../en/reference/plan-structure.md)

Эта страница перечисляет разделы каждого артефакта Specadoc и лимиты размера.
Для каждого раздела указано, кто его пишет: команда или человек вручную.
Шаблоны находятся в
[`skills/specadoc/assets/`](../../../skills/specadoc/assets/). Причины, по
которым так устроены артефакты и гейты, описаны на странице
[Артефакты и гейты](../concepts/artifacts-and-gates.md).

`<root>` — корень артефактов, по умолчанию `docs/specadoc` (см.
[Конфигурация](config.md#корень-артефактов)). `<skill-root>` — установленная
папка `skills/specadoc`.

## Структура корня артефактов

| Путь | Содержимое | Время жизни |
|---|---|---|
| `<root>/<slug>/spec.md` | Поведенческий контракт одного изменения | До архивации |
| `<root>/<slug>/plan.md` | Задачи, решения, одобрения и доказательства | До архивации |
| `<root>/<slug>/design.md` | Решения по дизайну, только если они требуются | До архивации |
| `<root>/<slug>/research.md` | Доказательства исследования, только если они требуются | До архивации |
| `<root>/<slug>/runs/` | Временные файлы передачи между ролями, git их игнорирует | Удаляются при архивации |
| `<root>/archive/<slug>/record.md` | Компактная запись закрытого изменения | Постоянно, повторно не открывается |
| `<root>/specs/<capability>.md` | Текущее поведение одной возможности | Постоянно, обновляется изменениями |
| `<root>/contracts/<contract>.md` | Межсервисный контракт в репозитории общего пакета | Постоянно |

`init_change.py` создаёт `spec.md` и `plan.md` из шаблонов. С флагами
`--with-design` и `--with-research` он также создаёт `design.md` и
`research.md`. Скрипт заполняет название, риск, дату и поле scout. Если процесс
репозитория с более высоким приоритетом не требует `tasks.md`, не создавайте
этот файл.

## Кто что пишет

В таблицах ниже «вручную» означает, что текст правит контроллер или
пользователь. Имя команды в таблице указывает шаг скрипта, который пишет
текст. Не правьте текст, который пишет команда. Вместо этого запустите команду
снова.

## spec.md

`spec.md` — стабильный поведенческий контракт. После одобрения он мало
меняется. Шаблон:
[`spec-template.md`](../../../skills/specadoc/assets/spec-template.md).

| Раздел | Обязателен | Кто пишет | Содержимое |
|---|---|---|---|
| Шапка: `Status`, `Risk`, `Created` | Да | `init_change.py` (риск, дата), вручную (статус) | Одно значение риска. Оно должно совпадать с шапками плана и дизайна. |
| `## Goal` | Да | вручную | Наблюдаемый результат для пользователя или системы. |
| `## Non-goals` | Да | вручную | Поведение, которое изменение исключает. |
| `## Current context` | Да | вручную | Только текущее поведение и ограничения, без которых изменение не понять. |
| `## Affected capabilities` | Да | вручную | Операции над возможностями, см. ниже. |
| `## Requirements` | Да | вручную | Блоки `### R<n> — <name>` с наблюдаемым поведением, которое можно проверить тестом. |
| `## Acceptance scenarios` | Да | вручную | Блоки `### A<n> — <name>` с `Covers:`, `Given:`, `When:` и `Then:`. |
| `## Constraints` | Да | вручную | Ограничения совместимости, безопасности, платформы, зависимостей и производительности. |
| `## Assumptions` | Да | вручную | Безопасные значения по умолчанию, которые выбраны вместо вопросов с малым влиянием. |
| `## Requirement coverage` | Да | вручную | Таблица, которая связывает каждое требование с его сценариями. |

Правила:

- Каждое поведенческое требование связано хотя бы с одним сценарием приёмки.
- Требования не содержат путей к файлам, классов, фреймворков и порядка
  реализации.
- Когда спецификация готова, не остаётся открытых вопросов, которые меняют
  поведение.

Снимок ревью охватывает четыре раздела спецификации: Requirements, Acceptance
scenarios, Constraints и Affected capabilities. Если они меняются после PASS
ревью, PASS устаревает. `approve` сохраняет хеш `spec.md` и `design.md` в
`runs/approval.json`.

### Affected capabilities

Раздел перечисляет каждую спецификацию возможности, а под ней операции над её
требованиями `C<n>`:

```text
- `docs/specadoc/specs/platform-connection-storage.md`
  - RENAMED C2 (R3) — The identifier is a `cnx_` ULID
  - REMOVED C3 (R6)
  - MODIFIED C5 (R6) — deleting a bound application no longer detaches the connection
  - ADDED C8 (R7) — A connection carries an owning agency
```

- Пишите операции в порядке `RENAMED`, `REMOVED`, `MODIFIED`, `ADDED`.
- Укажите хотя бы одно требование в скобках после id `C<n>`. Укажите каждое
  требование, которое реализует операция.
- Для новой спецификации возможности напишите `(new capability)` после пути.
  Тогда допустима только операция `ADDED`.

`validate_change.py --phase spec` проверяет синтаксис и порядок. Он также
проверяет, что каждый id `MODIFIED`, `REMOVED` и `RENAMED` существует в
целевом файле. Ещё он проверяет, что ни один id `ADDED` не совпадает с
существующим. Финальный гейт
(`validate_change.py --phase final`) и `archive_change.py` проверяют, что
спецификация возможности содержит результат.

## plan.md

`plan.md` — изменяемое техническое состояние: задачи, решения, одобрения и
доказательства. Шаблон:
[`plan-template.md`](../../../skills/specadoc/assets/plan-template.md).
Шаблон нормативный. Изменение шаблона меняет гейт плана.

| Раздел | Обязателен | Кто пишет | Содержимое |
|---|---|---|---|
| Шапка: `Status`, `Mode`, `Specification`, `Risk`, `Scout`, `Created` | Да | `init_change.py`, `approve` (статус) | `approve` ставит `Status: Approved, apply not started`. |
| `## Handoff` | Да | вручную, `approve` и `review-result` (`Plan checkpoint`) | Контрольная точка плана, `### Read before continuing`, `### Completed phases`, `### Continue with`. |
| `## Reconnaissance evidence` | Да | вручную | Не больше 8 путей или символов, 5 паттернов для повторного использования, точные команды проверки, подтверждённые ограничения. |
| `## Confirmed decisions` | Да | вручную, `design-brief --attempt-decision continue:` | Одна строка на каждое принятое решение с указанием, кто его принял. |
| `## Technical approach` | Да | вручную | Пишется после готовности спецификации. |
| `## Migration matrix` | Условный | вручную | Только для механических миграций пространств имён, путей, символов или типов. В остальных случаях удалите раздел. |
| `## Global constraints` | Да | вручную, `design-brief --attempt-decision accept:` | Ограничения для всех задач. Сюда попадают обязательства дизайна. |
| `## Files and interfaces` | Да | вручную | Таблица: путь или символ, действие и ответственность. |
| `## Class inventory` | Условный | вручную | Каждый новый нетестовый файл: файл, слой, причина, вид (`port`, `concrete` или `file`). Если изменение не добавляет таких файлов, удалите строку-пример. |
| `## Design review` | Если есть Class inventory | `design-review` | Вердикт дизайна. Он привязан к хешу реестра классов. |
| `## Tasks` | Да | вручную, `accept`, `amend`, `external-result` | Блоки `### T<n> — <outcome>`, см. [Поля задачи](#поля-задачи). |
| `## Requirement-to-check matrix` | Да | вручную, `finalize --requirements` (статус) | Одна строка на каждое требование: сценарии, точная проверка, статус. |
| `## Plan approval` | Да | `approve` | `Status`, `Bindings shown`, `Approved at`, `Approval provenance`. |
| `## Review scope` | Перед ревью | `scope` | Один путь файла относительно корня репозитория в обратных кавычках на каждый пункт списка. `!path` для удалённого файла. |
| `## Final verification` | Да | `finalize` | Чекбоксы и строка `Observed (<time>):`. |
| `## Review result` | Да | `pre-review`, `review-result` | `Result`, `Reviewed requirements`, `Reviewed tasks`, `### Findings`, `### Round log`. |
| `## Archive summary` | Да | вручную | Долговременный результат, принятые решения, влияние на возможности и остаточные риски. |
| `## Completion evidence` | Да | `finalize`, `collect_tokens.py --append` | Команды, связь с требованиями, токены исполнения, раунды ревью, остаточные риски. |

`validate_change.py` требует разделы с отметкой «Да». Удаляйте только те
разделы, которые шаблон отмечает как условные.

### Handoff

Заметки сессии не входят в `plan.md`. Записывайте их в `runs/handoff.md`
командой `specadoc_step.py handoff <slug> --file -`. Шаг каждый раз
перезаписывает файл.

`### Read before continuing` — стартовый список новой сессии `apply`. Список
называет вывод `status`, `runs/handoff.md`, `spec.md`, `plan.md`, файл дизайна
или исследования и не больше пяти критичных путей репозитория.

### Поля задачи

Блок задачи начинается с `### T<n> — <independently testable outcome>` и
чекбокса `- [ ] Complete`. Каждое поле — пункт списка
`- **<Field>:** <value>`.

Обязательные поля (по валидатору):

| Поле | Содержимое |
|---|---|
| `Requirements` | Id `R<n>`, которые реализует задача. |
| `Risk` | Риск задачи. |
| `Decision risk` | `low`, `medium` или `high`. Для `Owner: worker` нужно `low`. |
| `Owner` | `worker` или `controller`. |
| `Verification owner` | `worker` или `controller`. Только для задач `worker`. Для задач контроллера удалите это поле. |
| `Files` | Пути, папки или маски в обратных кавычках. Символы указывают в скобках после пути. |
| `Test first` | Конкретный поведенческий тест. |
| `Expected RED` | Почему тест сначала падает. |
| `Implementation` | Минимальное техническое направление. |
| `Verification` | Точные команды, каждая в обратных кавычках, через точку с запятой. Больше ничего. |
| `Surface` | `code`, `ui` или `mixed`. |
| `Delivery verification` | Для `ui` и `mixed`: сборка, проверка типов и проверка в браузере. Для `code`: `N/A`. |
| `Done when` | Объективное условие завершения. |
| `Evidence` | Пишет `accept`. Одна или две строки. |

Другие поля шаблона:

| Поле | Содержимое |
|---|---|
| `Depends on` | Более ранние задачи или `None`. |
| `Decisions` | Принятые технические решения для этой задачи. |
| `Interfaces` | Текущие контракты, пути-образцы, нужная связка, экспорты, lock-файлы и тесты. |
| `Open decisions` | Перед отправкой задачи `worker` должно быть `None`. |
| `Controller justification` | Почему задача, готовая для `worker`, остаётся у контроллера. |
| `Derived files` | Сгенерированные или связующие пути, которые задача тоже может изменить. Изменения в них перечисляются и не считаются нарушениями. |
| `Obligations` | Идентификаторы обязательств дизайна из `## Global constraints`, которые выполняет эта задача (`R3.1, F1.2`). `approve` требует, чтобы каждое обязательство было названо в какой-то задаче. |
| `TDD exception` | Одобренное исключение и его детерминированная проверка. Для изменений поведения оставьте `None`. |
| `Verification inputs` | Конфигурации, тестовые хелперы, пути инструментов и манифесты, которые `Verification` использует только для чтения. Права на запись поле не даёт. |
| `Test context` | Образец теста, хелпер начальной настройки, окружение только для тестов и один раздел ранбука. |
| `External verification` | Запуск, который контроллер не должен выполнять: кто его выполняет и когда. |
| `Checkpoint` | Необязательная промежуточная точка коммита. Раунд ревью она не добавляет. |
| `Evidence hash` | Пишет `accept`, или его пишут вручную командой `validate_change.py --files-hash`. |
| `Accepted result` | Пишет `accept`: выданный результат, не больше 400 символов из сводки `worker`. |

`accept` отмечает чекбокс `Complete` и пишет `Evidence`, `Evidence hash` и
`Accepted result`. `dispatch --reopen` снимает отметку с чекбокса. `amend` —
единственный способ изменить область или замороженное `Verification`
отправленной задачи.

### Review result и Round log

`pre-review` добавляет один блок `### G<n>` в `### Round log` для каждого
запуска `reviewer`. `review-result` закрывает этот блок. Закрытый раунд
неизменяем. Блок раунда содержит такие поля:

| Поле | Кто пишет |
|---|---|
| `Type` (`initial` или `re-review`) | `pre-review` |
| `Snapshot` | `pre-review` |
| `Policy snapshot` | `pre-review` |
| `Previous` | `pre-review` |
| `Outcome` | `pre-review` (Pending), `review-result` (PASS или FAIL) |
| `Reason` | `pre-review` |
| `Review decision` | `pre-review --review-decision` |
| `Manifest` | `pre-review`, путь `runs/G<n>-manifest.json` |
| `Reviewer verdict`, `Reviewer agent`, `Result source`, `Result digest` | `review-result` |
| `#### Recorded findings` | `review-result` |

Устаревший снимок даёт `Outcome: FAIL` с `Snapshot status: stale` и
`Stale reason`. Вердикт `reviewer` остаётся в блоке.

У каждого замечания есть уровень: `BLOCKER`, `IMPORTANT` или `MINOR`.

После первого настоящего раунда `finalize` удаляет текст шаблона из журнала
раундов.

### Completion evidence

| Блок | Кто пишет |
|---|---|
| `Commands:` | `finalize`, из `runs/final-verification.json` или строки `Observed` |
| `Requirement mapping:` | `finalize`, из матрицы |
| `Execution tokens:` | `collect_tokens.py --append` |
| `Review rounds:` | `finalize`, из блоков `### G<n>` |
| `Residual risks or waivers:` | `finalize --residual` |

Каждый вызов `finalize` заново пишет эти блоки из записанного состояния.

## Условные артефакты

Если выполнено одно из этих условий, создайте `design.md`. Иначе не создавайте
его.

- Затронуто больше одного сервиса или крупного модуля.
- Меняется публичный API, контракт событий или постоянная схема.
- Миграция или откат нетривиальны.
- Безопасность, приватность, конкурентность, распределённое поведение или
  производительность находятся в центре изменения.
- У нескольких архитектур существенно разные компромиссы.

Если доказательства не помещаются в `plan.md` в сжатом виде, создайте
`research.md`. Иначе не создавайте его.

### design.md

Шаблон:
[`design-template.md`](../../../skills/specadoc/assets/design-template.md).
Все разделы пишут вручную.

| Раздел | Содержимое |
|---|---|
| Шапка: `Status`, `Risk`, `Created` | Риск должен совпадать со спецификацией и планом. |
| `## Context` | Почему нужно отдельное решение по дизайну. |
| `## Decision drivers` | Ограничения и атрибуты качества. |
| `## Options considered` | `### Option <n> — <name>` с преимуществами, затратами и рисками. |
| `## Decision` | Выбранный подход и причина выбора. |
| `## Interfaces and data flow` | Контракты, переходы состояний, события и схемы. |
| `## Migration and rollback` | Только если это относится к изменению. |
| `## Risks and mitigations` | Каждый риск и мера по его снижению. |

`## Interfaces and data flow` может содержать одну диаграмму PlantUML на
каждый аспект в блоке кода `plantuml`. Используйте диаграмму только в таких
случаях:

- диаграмма последовательности для цепочки вызовов, в которой участвуют
  больше двух сервисов или процессов
- диаграмма состояний для жизненного цикла, где больше двух состояний или
  есть защищённый переход
- диаграмма активности для потока с ветвлениями или параллельными шагами.

Диаграмма — иллюстрация. Ни один валидатор её не проверяет. Если диаграмма
противоречит требованиям или коду, исправьте или удалите диаграмму.

### research.md

Шаблон:
[`research-template.md`](../../../skills/specadoc/assets/research-template.md).
Все разделы пишут вручную.

| Раздел | Содержимое |
|---|---|
| Шапка: `Created` | |
| `## Relevant files and symbols` | Путь или символ с коротким наблюдением. |
| `## Existing patterns` | Паттерны для повторного использования. |
| `## Verification commands` | Точные команды. |
| `## Constraints and external contracts` | Каждое ограничение с доказательством. |
| `## Decision-relevant conclusions` | Короткие выводы, которые влияют на спецификацию или план. |
| `## Material unknowns` | Не больше трёх. |

Храните пути, символы, команды, внешние контракты, ограничения и короткие
выводы. Не храните цепочки рассуждений и общий рассказ о репозитории.

## Спецификация возможности

Спецификация возможности — файл `<root>/specs/<capability>.md`. Он описывает
поведение, которое существует сейчас. Шаблон:
[`capability-template.md`](../../../skills/specadoc/assets/capability-template.md).

| Раздел | Содержимое |
|---|---|
| Шапка: `Status`, `Last updated` | `Last updated` меняется с каждым изменением, которое вносит вклад. |
| `## Scope` | Один абзац: поведение, за которое отвечает возможность, и граница этого поведения. |
| `## Current behavior` | Блоки `### C<n> — <name>`: `The system SHALL <observable behavior>.` |
| `## Invariants` | Условия, которые должны оставаться верными при будущих изменениях. |
| `## Key paths` | Не больше пяти точек входа или публичных контрактов. Только пути. |
| `## Provenance` | Строка таблицы `Change | Date | Effect` для каждого изменения, которое внесло вклад. |

Спецификация возможности никогда не перечисляет задачи, диффы, списки файлов
или историю. В `propose` и `apply` контроллер обновляет её из принятого
`spec.md` после PASS ревью, а не из диффа. В `light` дельту спецификации
пишут на месте до реализации.

`doctor.py` предупреждает о ключевом пути, которого не существует.

## Файл контракта

У изменения межсервисного контракта есть файл `<root>/contracts/<contract>.md`
в репозитории общего пакета. Шаблон:
[`contract-template.md`](../../../skills/specadoc/assets/contract-template.md).

| Раздел | Содержимое |
|---|---|
| Шапка | Пакет-владелец, сервис-производитель, версия, в которой появляется изменение. |
| `## Goal` | Наблюдаемое изменение контракта. |
| `## Surface` | Эндпоинт или метод SDK, изменение, ломающее ли оно совместимость (да или нет). |
| `## Breaking part` | Что существующие вызывающие стороны больше не могут делать и с какой версии. `None`, если изменение только добавляет. |
| `## Consumers` | Каждый репозиторий, которому нужен пакет: текущее ограничение, нужная версия, план, статус. |
| `## Verification` | Проверка производителя, тест и тег пакета, проверка для каждого потребителя. |

`spec.md` потребителя ссылается на `<package> <version>`, а не на текст
контракта.

## record.md

`archive_change.py` пишет `<root>/archive/<slug>/record.md`. Никто не правит
этот файл вручную. Запись неизменяема: чтобы изменить поведение из архива,
откройте новое изменение.

Запись начинается с front matter:

```text
---
schema: specadoc.archive/v1
slug: <slug>
archived_at: <UTC time>
status: archived | forced
---
```

| Раздел | Источник | Лимит для `--force` |
|---|---|---|
| `## Goal` | Goal из `spec.md` | 1200 байт |
| `## Outcome` | Archive summary из `plan.md`, плюс `migration-summary.md` для устаревших архивов | 2200 байт |
| `## Affected capabilities` | Affected capabilities из `spec.md` | 1800 байт |
| `## Decisions` | Confirmed decisions из `plan.md` | 1600 байт |
| `## Review` | Review result из `plan.md` без манифестов раундов, плюс запись tidy | 700 байт |
| `## Measurement` | Итоги по токенам из Completion evidence в `plan.md` | 900 байт |
| `## Forced exceptions` | Невыполненные гейты принудительной архивации или `None.` | |
| `## Source manifest` | Имя, размер и SHA-256 каждого исходного файла | |

В обычном архиве пустой раздел становится `Not recorded.` Принудительная
архивация обрезает каждый раздел до лимита из таблицы. Запись должна упоминать
каждый id `R<n>` и `C<n>` спецификации. Обязательные части: строка схемы,
строка слага, `## Goal`, `## Outcome` и `## Source manifest`.

Файлы в `runs/` сворачиваются в одну строку манифеста источников. Архивация
удаляет их вместе с папкой изменения.

## Что проверяет валидатор

`validate_change.py` проверяет только структуру:

- обязательные разделы
- id требований и сценариев и их покрытие
- операции над возможностями
- число задач и полноту полей задач
- значения владельцев
- незаполненные заполнители, например `<text>`, `Pending` или `TBD`
- пути области ревью
- последний раунд ревью.

Смысл валидатор проверить не может. Успешная валидация не делает
спецификацию принятой. Устаревшие изменения, которые созданы до появления
этих разделов, не обязаны проходить валидацию.

## Лимиты размера

| Объект | Лимит | Последствие |
|---|---|---|
| `plan.md` | 48 KiB | Предупреждение. Оно называет самые большие разделы. Ни один шаг его не ждёт. |
| Раздел `## Handoff` в `plan.md` | 2 KiB | Предупреждение. |
| `runs/handoff.md` | 4 KiB | `handoff` завершается с ошибкой. |
| Задачи в одном плане | 8 | Предупреждение, если задач больше 8. Обычно задач от трёх до восьми. |
| Бриф `worker` `runs/T<n>-brief.md` | 16 000 байт | Предупреждение, которое называет самые большие части. |
| `runs/lessons.md` в брифе | 2048 байт | Обрезается до лимита. |
| Принятый результат | 400 символов | Сводка `worker` обрезается. |
| `record.md` | 16 KiB | Архивация завершается с ошибкой. |
| `spec.md`, `plan.md`, `design.md`, `research.md` при архивации | 512 KiB | Предупреждение о вставленных логах. |
| Ключевые пути возможности | 5 | Правило шаблона. |
| Раунды ревью `initial` | 3 | Для четвёртого нужен `--review-decision`. Повторные ревью не учитываются. |
| Раунды ревью дизайна | 4 | Для следующего раунда после FAIL нужен `--attempt-decision`. |
| Контекст контроллера при `dispatch` и `design-brief` | 200k токенов (`context.dispatch_guard`) | Шаг останавливается. Запишите передачу сессии и продолжите в новой сессии. |

байт. Для каждого режима задан общий лимит на `SKILL.md` и справочники,
которые режим всегда загружает.

| Режим | Общий лимит (байт) |

| `explore` | 14336 |
| `light` | 12288 |
| `propose` | 31744 |
| `apply` | 11264 |
