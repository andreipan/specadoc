# Глоссарий

[English](../../en/reference/glossary.md)

На этой странице определены термины документации Specadoc. У каждого термина
одно значение, и документация использует один термин для каждого понятия.
После русского термина в скобках указан английский. Последний столбец
ссылается на страницу, где термин объяснён.

Имена ролей (`scout`, `worker`, `reviewer`), вердикты (`PASS`, `FAIL`), уровни
замечаний и статусы остаются постоянными английскими идентификаторами.

| Термин | Определение | Где объяснено |
|---|---|---|
| **BLOCKED** | Статус `worker`: `worker` не может продолжить без решения. Также результат `specadoc_step.py`: шаг не может провести оценку. | [Роли](../concepts/roles.md#worker) |
| **DONE** | Статус `worker`: задача выполнена. | [Роли](../concepts/roles.md#worker) |
| **DONE_WITH_CONCERNS** | Статус `worker`: задача выполнена, но `worker` сообщает об опасениях. Контроллер принимает решение по каждому опасению до приёмки. | [Роли](../concepts/roles.md#worker) |
| **EXTERNAL-PENDING** | Результат `accept` для задачи с `External verification:`. Зависимые задачи и ревью могут начаться. Финальному гейту нужен записанный PASS. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#внешняя-проверка) |
| **NEEDS_CONTEXT** | Статус `worker`: `worker` нужен названный контекст. Контроллер добавляет его и снова отправляет задачу. Это не считается неудачной попыткой. | [Роли](../concepts/roles.md#worker) |
| **reviewer** | Роль только на чтение. Она проверяет стабильный дифф или реестр классов в гейте дизайна и возвращает вердикт. | [Роли](../concepts/roles.md#reviewer) |
| **scout** | Роль только на чтение. Она отвечает на один ограниченный вопрос о коде и возвращает короткий отчёт. | [Роли](../concepts/roles.md#scout) |
| **worker** | Роль, которая реализует одну готовую задачу в пределах её `Files` и возвращает отчёт со статусом. | [Роли](../concepts/roles.md#worker) |
| **архивная запись** (record, `record.md`) | Компактный неизменяемый архив закрытого изменения, `<root>/archive/<slug>/record.md`, не больше 16 KiB. | [Структура плана](plan-structure.md#recordmd) |
| **базовый снимок** (baseline) | Манифест содержимого рабочего дерева. Шаг `dispatch` записывает его в `runs/T<n>-baseline.json` до начала задачи. При повторной попытке остаётся первый базовый снимок. | [Скрипты](scripts.md#review_snapshotpy) |
| **бриф задачи** (task brief) | Самодостаточный файл `runs/T<n>-brief.md`, который читает `worker`. Его пишет `dispatch`. | [Скрипты](scripts.md#task_briefpy) |
| **вердикт** (verdict) | Результат ревью: `PASS` или `FAIL`. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#раунды-ревью) |
| **внешний запуск** (external dispatch) | Запуск роли через `run_role.py` на рантайме, который отличается от рантайма контроллера. | [Маршрутизация](../guides/routing.md) |
| **внешняя проверка** (external verification) | Обязательная проверка, которую может выполнить только пользователь или другой исполнитель. Задача называет её в `External verification:`, а `external-result` записывает её результат. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#внешняя-проверка) |
| **гейт** (gate) | Детерминированная проверка между фазами, например `validate_change.py --phase plan`, гейт дизайна или гейты архивации. Непройденный гейт блокирует следующий шаг. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#гейты) |
| **гейт дизайна** (design gate) | Проверка перед одобрением плана: независимый `reviewer` проверяет реестр классов. Для `dispatch` нужен текущий PASS. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#гейт-дизайна) |
| **дельта спецификации** (spec delta) | Изменение спецификаций возможностей, которое лёгкое изменение пишет на месте: затронутые утверждения `C<n>`, инварианты и ключевые пути. | [Жизненный цикл](../concepts/lifecycle.md#light) |
| **дисциплина контекста** (context discipline) | Правила, которые держат контекст контроллера небольшим: без повторного чтения, сырых логов успешных запусков и обходов репозитория, с компактным выводом шагов. | [Роли](../concepts/roles.md#дисциплина-контекста) |
| **доказательства** (evidence) | Запись в одну-две строки: команды и результаты, которые подтверждают задачу. Её пишет `accept`. | [Структура плана](plan-structure.md#поля-задачи) |
| **замечание** (finding) | Одна проблема, о которой сообщает `reviewer`: уровень `BLOCKER`, `IMPORTANT` или `MINOR`, место и краткое описание. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#раунды-ревью) |
| **изменение** (change) | Одна единица работы со слагом. У изменения с полным жизненным циклом есть папка изменения. У лёгкого изменения её нет. | [Жизненный цикл](../concepts/lifecycle.md) |
| **исполнение** (execution) | Один прогон для учёта токенов: один транскрипт контроллера или один дочерний агент. | [Скрипты](scripts.md#collect_tokenspy) |
| **исполнитель** (executor) | Единственный постоянный агент, которому foreman делегирует практическую работу. | [Оркестратор и foreman](../guides/orchestrator-and-foreman.md#foreman) |
| **контроллер** (controller) | Основная сессия агента. Контроллер отвечает за решения, одобрения, финальную проверку и артефакты. | [Роли](../concepts/roles.md#кто-что-решает) |
| **контрольная точка плана** (plan checkpoint) | Остановка после `propose`, на которой пользователь одобряет план. Это единственная остановка для одобрения в `propose`. | [Жизненный цикл](../concepts/lifecycle.md#propose) |
| **корень артефактов** (artifact root) | Папка со всеми файлами Specadoc в репозитории. По умолчанию это `docs/specadoc`. | [Конфигурация](config.md#корень-артефактов) |
| **лёгкое изменение** (light change) | Изменение в режиме `light`: одна сессия, только спецификации возможностей, без папки изменения. | [Light или propose](../guides/light-or-propose.md) |
| **лимит раундов** (round cap) | Ограничение числа раундов ревью: три раунда ревью `initial` (для четвёртого нужен `--review-decision`) и четыре раунда дизайна (для следующего нужен `--attempt-decision`). | [Артефакты и гейты](../concepts/artifacts-and-gates.md#раунды-ревью) |
| **мандат** (mandate) | Полномочия, которые пользователь явно даёт оркестратору, например одобрять обычные локальные планы. | [Оркестратор и foreman](../guides/orchestrator-and-foreman.md#мандат) |
| **нативный запуск** (native dispatch) | Запуск роли как субагента контроллера на рантайме контроллера. | [Роли](../concepts/roles.md#как-определяется-роль) |
| **область ревью** (review scope) | Список `## Review scope`: пути файлов исполняемого диффа относительно корня репозитория. Его пишет `specadoc_step.py scope`. | [Структура плана](plan-structure.md#planmd) |
| **обоснование контроллера** (controller justification) | Поле задачи. Оно объясняет, почему задача, готовая для `worker`, остаётся у контроллера. | [Роли](../concepts/roles.md#worker) |
| **обязательство дизайна** (design obligation) | Открытый пункт IMPORTANT из раунда дизайна с FAIL, который контроллер принимает после лимита раундов. Пункт попадает в `## Global constraints` и обязателен для `apply`. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#гейт-дизайна) |
| **ограничитель контекста** (context guard) | Предел контекста контроллера, около 200k токенов (`context.dispatch_guard`). На этом пределе `dispatch` и `design-brief` останавливаются, и контроллер пишет передачу сессии. | [Роли](../concepts/roles.md#границы-сессий) |
| **одобрение** (approval) | Решение пользователя, которое записано в `plan.md` командой `specadoc_step.py approve`. Оркестратор может дать одобрение по записанному мандату пользователя. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#одобрения) |
| **операция над возможностью** (capability operation) | Одна строка под спецификацией возможности в `## Affected capabilities`: `ADDED`, `MODIFIED`, `REMOVED` или `RENAMED` для требования `C<n>` с id `R<n>`, на которые она ссылается. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#операции-над-возможностями) |
| **отправка задачи** (dispatch) | Шаг `specadoc_step.py dispatch`. Шаг проверяет задачу, пишет её базовый снимок и бриф и передаёт задачу `worker` или контроллеру. | [Роли](../concepts/roles.md#worker) |
| **папка изменения** (change folder) | Папка `<root>/<slug>/` с `spec.md`, `plan.md`, необязательными `design.md` и `research.md` и папкой `runs/`. | [Структура плана](plan-structure.md#структура-корня-артефактов) |
| **передача сессии** (handoff) | Компактные заметки сессии в `runs/handoff.md` (не больше 4 KiB). По ним новая сессия продолжает изменение. `specadoc_step.py handoff` перезаписывает этот файл. | [Роли](../concepts/roles.md#границы-сессий) |
| **переносимый контракт роли** (portable role contract) | Файл инструкции роли `references/roles/<role>.md`. Контроллер передаёт его субагенту, если нет роли проекта или плагина. Файл задаёт поведение, а не модель. | [Роли](../concepts/roles.md#как-определяется-роль) |
| **план** (plan, `plan.md`) | Изменяемое техническое состояние изменения: задачи, решения, одобрения, доказательства и итог для архива. | [Структура плана](plan-structure.md#planmd) |
| **повторное открытие** (reopen) | Новая попытка более ранней задачи от текущего дерева. Её запускает команда `dispatch --reopen '<reason>'`. Используйте повторное открытие только для исправлений кода. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#поправка-повторное-открытие-и-исключение) |
| **повторное ревью** (re-review) | Целевое ревью прежних замечаний и изменённых файлов после исправления. Оно не учитывается в лимите раундов. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#раунды-ревью) |
| **поле `Verification`** (Verification) | Поле задачи с точными командами, которые запускает `accept`. При отправке задачи поле замораживается. | [Структура плана](plan-structure.md#поля-задачи) |
| **поправка** (amendment) | Записанное изменение области или замороженного `Verification` отправленной задачи. Поправку вносят командой `specadoc_step.py amend` и указывают причину. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#поправка-повторное-открытие-и-исключение) |
| **привязка роли** (role binding) | Рантайм, модель и уровень усилий, которые обслуживают роль. Каждый запуск роли определяет привязку заново. | [Конфигурация](config.md#как-определяется-привязка-роли) |
| **приёмка** (acceptance) | Шаг `specadoc_step.py accept`. Шаг проверяет область задачи и отчёт, запускает `Verification` задачи и записывает `Evidence`. Отправка задачи не означает приёмку. | [Роли](../concepts/roles.md#worker) |
| **проба** (probe) | Проверка `doctor.py --probe` для оболочки, в которой работает сессия. | [Конфигурация](config.md#verificationprobe) |
| **производные файлы** (derived files) | Поле задачи со сгенерированными или связующими путями, которые задача тоже может изменить, например lock-файлами. Изменения в них перечисляются и не считаются нарушениями. | [Структура плана](plan-structure.md#поля-задачи) |
| **проход tidy** (tidy pass) | Один проход `worker` по области ревью перед первым ревью `initial`. Проход чистит код и сохраняет поведение. | [Сопутствующие скиллы](../guides/companion-skills.md) |
| **рантайм** (runtime) | CLI агента, в котором работает роль: `claude`, `codex` или `opencode`. | [Маршрутизация](../guides/routing.md) |
| **расхождение** (drift) | Различие между спецификацией возможности и кодом. Верным считается код. Контроллер сообщает о расхождении. | [Жизненный цикл](../concepts/lifecycle.md#explore) |
| **раунд ревью** (review round) | Один блок `### G<n>` в журнале раундов `plan.md`. `pre-review` записывает его, а `review-result` закрывает. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#раунды-ревью) |
| **ревью** (review) | Одна независимая проверка стабильного диффа ролью `reviewer` только на чтение. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#раунды-ревью) |
| **реестр классов** (class inventory) | Таблица `## Class inventory` в `plan.md`. В ней перечислен каждый новый нетестовый файл: слой, причина и вид (`port`, `concrete` или `file`). | [Артефакты и гейты](../concepts/artifacts-and-gates.md#гейт-дизайна) |
| **режим** (mode) | Одна из пяти фаз Specadoc: `explore`, `propose`, `apply`, `light` или `archive`. | [Режимы](modes.md) |
| **риск** (risk) | Значение `low`, `medium` или `high` в шапках спецификации, плана и дизайна. Три шапки должны совпадать. | [Структура плана](plan-structure.md#specmd) |
| **риск решений** (decision risk) | Поле задачи со значением `low`, `medium` или `high`: риск решений, которые остаются тому, кто реализует задачу. Для `Owner: worker` нужно `low`. | [Структура плана](plan-structure.md#поля-задачи) |
| **роль** (role) | Ограниченная работа агента с фиксированным контрактом: `scout`, `worker` или `reviewer`. | [Роли](../concepts/roles.md) |
| **скилл** (skill) | Пакет инструкций, который загружает хост, например `specadoc` или `orchestrator`. | [Установка](../guides/install.md) |
| **слаг** (slug) | Короткий id изменения в формате kebab-case. Это же имя папки изменения. | [Структура плана](plan-structure.md#структура-корня-артефактов) |
| **снимок ревью** (review snapshot) | Отсортированный манифест `{path: sha256}` области ревью и разделов контракта спецификации. PASS действует, только пока снимок не изменился. | [Артефакты и гейты](../concepts/artifacts-and-gates.md#когда-pass-остаётся-действительным) |
| **сопутствующий скилл** (companion skill) | Необязательный скилл, который Specadoc использует для одного шага: `tidy`, `codebase-design`, `domain-modeling` или равноценный скилл хоста. | [Сопутствующие скиллы](../guides/companion-skills.md) |
| **спецификация** (spec, `spec.md`) | Стабильный поведенческий контракт изменения: цель, требования, сценарии приёмки, ограничения и операции над возможностями. | [Структура плана](plan-structure.md#specmd) |
| **спецификация возможности** (capability spec) | Долгоживущий файл `<root>/specs/<capability>.md`. Он описывает текущее наблюдаемое поведение одной возможности утверждениями `C<n>`. | [Артефакты и гейты](../concepts/artifacts-and-gates.md) |
| **строка происхождения** (provenance row) | Строка `<slug> \| <date> \| <effect>` в таблице `## Provenance` спецификации возможности, по одной на каждое изменение, которое внесло в неё вклад. | [Структура плана](plan-structure.md#спецификация-возможности) |
| **сценарий приёмки** (acceptance scenario) | Блок `### A<n>` в `spec.md` с `Given`, `When` и `Then`. Каждое требование связано хотя бы с одним сценарием. | [Структура плана](plan-structure.md#specmd) |
| **требование** (requirement) | Блок `### R<n>` в `spec.md` с наблюдаемым поведением, которое можно проверить тестом. | [Структура плана](plan-structure.md#specmd) |
| **управляющий скилл** (management skill) | Скилл, который управляет другими агентами: `foreman` или `orchestrator`. Пользователь запускает его явно. | [Оркестратор и foreman](../guides/orchestrator-and-foreman.md) |
| **устаревшие доказательства** (stale evidence) | Принятые доказательства, у которых после приёмки изменились файлы, команды или окружение. `specadoc_step.py refresh` снова принимает задачу. | [Конфигурация](config.md#verificationenvironment) |
| **файл контракта** (contract file) | Файл `<root>/contracts/<contract>.md` в репозитории общего пакета. Он описывает изменение межсервисного контракта и его потребителей. | [Структура плана](plan-structure.md#файл-контракта) |
| **финальная проверка** (final verification) | Однократный запуск всего набора тестов и гейтов репозитория перед первым ревью, а также чек-лист `## Final verification`. За неё отвечает контроллер. | [Жизненный цикл](../concepts/lifecycle.md#apply) |
