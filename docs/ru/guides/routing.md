# Маршрутизация ролей

[English](../../en/guides/routing.md)

Specadoc передаёт работу трём ролям: `scout`, `worker` и `reviewer` (см. [Роли](../concepts/roles.md)). В этом руководстве описано, как каждая роль получает рантайм, модель и уровень усилий и как изменить этот выбор.

Привязка роли состоит из четырёх частей: рантайм, модель, уровень усилий и файл, который их задаёт. Рантайм — это CLI агента, который запускает роль: `claude`, `codex` или `opencode`. Процесс Specadoc не закрепляет модель. Модель и уровень усилий всегда берутся из файла роли: из файла роли проекта или из роли, которую поставляет плагин.

Рантайм контроллера — это хост, в котором вы запустили Specadoc. Роль на рантайме контроллера работает как нативный субагент. Роль на другом рантайме работает как внешняя роль через `run_role.py`.

В командах ниже `<skill-root>` — установленная папка `skills/specadoc`. Запускайте команды из корня рабочей копии.

## Выбор роли без `.specadoc.json`

Если в проекте нет `.specadoc.json` с ключом `roles`, контроллер берёт первую роль из списка, которая существует:

1. Роль проекта в реестре рантайма контроллера: `.claude/agents/<role>.md`, `.codex/agents/<role>.toml` или `.opencode/agents/<role>.md`.
2. Зарегистрированная роль плагина, например `specadoc:<role>` в Claude Code.
3. Доступный субагент без зарегистрированной роли. Контроллер вставляет переносимый контракт роли (`references/roles/<role>.md`) в промпт отправки задачи. Контракт задаёт поведение, а не модель.
4. Субагентов нет. Контроллер может сам выполнить работу scout и worker.

В случае 4 контроллер не может получить независимый PASS от reviewer. Он сообщает о незавершённом гейте ревью и останавливается до управляемого завершения или обычной архивации. Контроллер никогда не заменяет reviewer собственным ревью.

Плагин для Claude Code поставляет три роли как `agents/*.md`. Их frontmatter задаёт псевдоним модели: `haiku` для scout, `sonnet` для worker и `opus` для reviewer. Источник этих значений — `scripts/claude-roles.json`. Роль проекта с тем же именем имеет приоритет.

В проекте без маршрутизации установленная устаревшая роль-обёртка всё ещё может выбрать другой рантайм (см. [Переход со старых настроек](#переход-со-старых-настроек)).

## Маршрутизация проекта через `.specadoc.json`

Файл `.specadoc.json` принадлежит проекту. Вы коммитите его, и его маршруты действуют для всех, кто запускает Specadoc в этой рабочей копии. Файл выбирает только рантайм каждой роли:

```json
{
  "version": 1,
  "roles": {
    "controller": {"runtime": "claude"},
    "scout": {"runtime": "claude"},
    "worker": {"runtime": "codex"},
    "reviewer": {"runtime": "claude"}
  }
}
```

Правила для ключа `roles`:

- `roles` требует `"version": 1`.
- Можно перечислить часть ролей и не указывать остальные.
- В каждой записи есть только ключ `runtime`. Модели, уровень усилий, разрешения и инструменты задаются в файлах ролей.
- Неизвестный ключ, роль, версия или рантайм — ошибка. Specadoc не подставляет вместо них значение по умолчанию без предупреждения.
- `roles.controller.runtime` не запускает контроллер. Ключ проверяет, что вы запустили Specadoc в ожидаемом хосте.

Полную схему и другие ключи (`root`, `verification`, `review`) см. в разделе [Конфигурация](../reference/config.md).

### Порядок выбора

Для каждой роли рантайм берётся из первого источника, который его задаёт:

1. `roles.<role>.runtime` в `.specadoc.json`.
2. Привязка по умолчанию у установленной устаревшей роли-обёртки в реестре контроллера.
3. Рантайм контроллера.

Затем модель и уровень усилий берутся из файла роли выбранного рантайма:

| Рантайм | Файл роли | Ключ модели | Ключ уровня усилий | Значения уровня усилий |
|---|---|---|---|---|
| `claude` | `.claude/agents/<role>.md` (frontmatter) | `model` | `effort` | `low`, `medium`, `high`, `max` |
| `codex` | `.codex/agents/<role>.toml` | `model` | `model_reasoning_effort` | `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra` |
| `opencode` | `.opencode/agents/<role>.md` (frontmatter) | `model` | `variant` | те же, что у `codex` |

Резолвер читает только эти файлы проекта. Текущие реестры плагинов хоста он не читает. Поэтому роли с маршрутом нужен файл роли проекта в целевом рантайме. Ошибкой считаются отсутствующий файл, пустая модель или модель-заглушка (`<...>`) и уровень усилий вне списка.

Если запись контроллера не совпадает с хостом, резолвер останавливается с сообщением `controller runtime is <host>, binding expects <runtime>`. Перезапустите Specadoc в ожидаемом хосте или исправьте `.specadoc.json`. Имя хоста `claude-code` принимается как `claude`.

### Согласие и независимость

Маршрут на рантайм, отличный от рантайма контроллера, — это согласие проекта. Specadoc отправляет в этот рантайм промпт роли и репозиторий и не спрашивает снова для каждого изменения или задачи. Запрос подтверждения от самого хоста Specadoc не контролирует.

Установите CLI каждого рантайма из маршрутов везде, где работает проект. Отсутствие CLI — ошибка. Specadoc никогда не подставляет вместо него другого провайдера.

Рекомендуем направлять reviewer на рантайм, отличный от рантайма worker, потому что у двух моделей одного производителя общие слепые зоны. Если `worker` и `reviewer` направлены на один рантайм, doctor выводит одно предупреждение на уровне проекта.

### Версия Python

Всем скриптам Specadoc нужен Python 3.10 или новее. Резолверу нужен Python 3.11 или новее, чтобы читать TOML-файлы ролей Codex. Если `python3` в вашем `PATH` старее, вызовите более новый интерпретатор явно.

## Проверка привязок

Чтобы увидеть привязки, которые будет использовать изменение, запустите эту команду. Она только читает файлы.

```text
python3 <skill-root>/scripts/role_routing.py --controller-runtime <runtime> --change <slug> --dry-run --compact --check-cli
```

Всегда указывайте рантайм контроллера. Не оставляйте его на угадывание.

Вывод — JSON с `routes` (роль, рантайм, модель, уровень усилий, запуск `native` или `external`) и `findings`. Код выхода равен 1, если одно из замечаний имеет уровень `ERROR`.

`--change <slug>` ограничивает ошибки ролями, которые использует план. План всегда использует reviewer. Worker план использует, если у задачи есть `Owner: worker`. Сломанный файл неиспользуемой роли даёт только предупреждение. `--check-cli` также проверяет, что CLI каждого рантайма есть в `PATH`.

Для проверки всего проекта запустите:

```text
python3 <skill-root>/scripts/doctor.py --controller-runtime <runtime>
```

CLI в `PATH` ещё не доказывает, что он запускается, что в нём выполнен вход и что модель доступна.

### Привязки при одобрении плана

Предпросмотр плана показывает по одной строке на роль (контроллер, scout, worker, reviewer): рантайм, модель, уровень усилий и файл-источник. PASS гейта дизайна записывает эту строку в `Bindings shown` в `plan.md`. Строка служит доказательством того, какие привязки будут работать. Привязку она не одобряет. В лёгком изменении контроллер показывает привязки контроллера и reviewer в чате.

Если привязка не соответствует риску изменения, предпросмотр добавляет одну строку совета. Пример: изменение с высоким риском, в котором reviewer работает на маленькой модели или с низким уровнем усилий. Строка называет точный файл и ключ, который нужно исправить. Specadoc не правит этот файл, не блокирует работу из-за совета и не записывает совет как одобрение. Вы можете исправить файл или продолжить без изменений.

## Повторный выбор привязки при каждой отправке задачи

Specadoc не хранит снимок, отпечаток или одобрение привязки. При каждой отправке задачи роль выбирается заново. Поэтому правка файла роли или `.specadoc.json` действует со следующей отправки задачи.

В проекте с маршрутизацией контроллер передаёт `--controller-runtime` в `specadoc_step.py dispatch` и `pre-review`. Эти шаги выводят `resolved <role> <runtime>/<model>/<effort>`. Если конфигурация сломана, шаги останавливаются до записи базового снимка. Если `--controller-runtime` не указан, шаги берут `roles.controller.runtime` и сообщают об этом.

## Роли на другом рантайме

`run_role.py` запускает роль через CLI другого рантайма и собирает её результат. Контроллер использует его, когда рантайм роли отличается от рантайма контроллера.

В проекте с маршрутизацией запускайте его с `--controller-runtime`:

```text
python3 <skill-root>/scripts/run_role.py start --role worker --controller-runtime <runtime> --prompt-file <root>/<slug>/runs/T1-brief.md --name T1
python3 <skill-root>/scripts/run_role.py wait <run-file> --timeout 540 --shell-budget 590 --follow
python3 <skill-root>/scripts/run_role.py result <run-file>
```

Раннер выбирает привязку роли при запуске. Он отклоняет явные `--runtime`, `--model` или `--effort`, если они противоречат выбранной привязке. Привязку он записывает в файл запуска. Без маршрутизации укажите `--runtime`, `--model` и `--effort` явно.

| Команда | Что делает |
|---|---|
| `start` | Запускает CLI в фоне и сразу возвращает файл запуска. С `--dry-run` выводит команду и ничего не записывает. |
| `status <run-file>` | Показывает состояние (выполняется, завершён, сбой, нет прогресса), статус роли и прошедшее время. |
| `wait <run-file>` | Ждёт не дольше `--timeout` секунд. С `--follow` выводит строку прогресса, по умолчанию каждые 45 секунд. |
| `result <run-file>` | Проверяет итоговый JSON по схеме роли и сохраняет его. |
| `stop <run-file>` | Останавливает запуск, от которого вы отказались. |

Файлы запуска попадают в папку файла промпта, обычно в `runs/` изменения. Пути для `--prompt-file`, `--out-dir` и `--cwd` задаются относительно `--cwd`.

Коды выхода:

- `wait` возвращает 3, если таймаут истёк, а роль ещё работает. Это не сбой. Снова дождитесь того же запуска.
- `start` возвращает 4 (`sandboxed:`), если рантайм не может запуститься внутри песочницы оболочки. Запустите ту же команду вне песочницы с повышением прав средствами хоста и сошлитесь на маршрутизацию.
- `result` возвращает 1, если CLI завершился с ошибкой или JSON не соответствует схеме. Перед повтором прочитайте лог, который указан в файле запуска.
- Любая команда возвращает 2 при ошибке использования или конфигурации.

Если у инструмента оболочки есть ограничение по времени, задайте его больше `--shell-budget`. Если поднять ограничение нельзя, ждите короткими отрезками, например `--timeout 110 --shell-budget 120`.

Если имя и вызов совпадают, повторный старт использует существующий запуск. Если изменился промпт или привязка, нужно новое имя.

### Что получает внешняя роль

| Рантайм | Как раннер её запускает |
|---|---|
| `codex` | `codex exec`. Worker получает `-s workspace-write` с доступом к loopback-сети. Scout и reviewer получают `-s read-only`. |
| `claude` | `claude -p` с `--json-schema`. Worker получает инструменты правки. Scout и reviewer получают `Read, Grep, Glob, Bash`. |
| `opencode` | `opencode run --standalone --format json --auto` с отдельным основным агентом. Scout и reviewer получают инструменты чтения и поиска и команды `git` только для чтения. |

Scout или reviewer в OpenCode также получает команды оболочки, которые разрешает установленный файл роли. Это записи `action: shell`, `effect: allow` из его списка `permissions`. Это разрешения инструментов, а не песочница ОС.

Внешняя роль не получает MCP-серверы и контекст контроллера. Назовите точные файлы в её брифе.

Для worker контроллер оборачивает запуск в обмен через файлы: `specadoc_step.py dispatch` перед `start` и `specadoc_step.py accept` после `result`. Полный список шагов см. в разделе [Скрипты](../reference/scripts.md).

## Блок инструментов в файлах ролей

В каждом контракте роли, который поставляет плагин, есть один блок между `<!-- specadoc:tooling:begin -->` и `<!-- specadoc:tooling:end -->`. В блоке нейтральные советы по инструментам поиска. Например, scout использует инструмент с поиском по символам или по графу кода, если такой есть в рантайме. Иначе scout ищет ограниченными запросами `rg`.

Если ваш хост генерирует собственные файлы ролей, можно заменить только этот блок своими советами по инструментам. Остальную часть роли и формат отчёта сохраните.

Источник — переносимые контракты в `skills/specadoc/references/roles/`. Файлы Claude в `agents/*.md` генерирует из них `scripts/render_roles.py`. Метаданные Claude хранятся в `scripts/claude-roles.json` и не задают модели Codex.

## Изменение привязки

Чтобы изменить модель или уровень усилий роли:

1. Найдите файл-источник в строке привязок или в выводе `role_routing.py`.
2. Измените `model` или ключ уровня усилий в этом файле.
3. Снова запустите `role_routing.py` и проверьте результат.

Следующая отправка задачи использует новые значения. Модель контроллера дешевле всего менять на границе сессии, потому что кеш промптов привязан к одной модели.

Чтобы перенести роль на другой рантайм:

1. Установите CLI целевого рантайма везде, где работает проект.
2. Установите файл роли в реестр целевого рантайма.
3. Задайте `roles.<role>.runtime` в `.specadoc.json`. Если `version` нет, добавьте `"version": 1`.
4. Запустите `role_routing.py` с `--check-cli`.
5. Закоммитьте `.specadoc.json`, потому что маршрут действует для всех.

## Переход со старых настроек

Обновление плагина не перезаписывает `.specadoc.json` и ваши файлы ролей.

`.specadoc.json` только с корнем (`{"root": "<path>"}`) остаётся допустимым, и `version` в нём не нужен. Если вы добавляете `roles`, добавьте `"version": 1`.

Устаревшая роль-обёртка содержит строку такого вида:

```text
Default binding: runtime `codex`, model `<model>`, effort `<effort>`
```

Без `roles` в `.specadoc.json` привязка по умолчанию из обёртки продолжает действовать. Строка `Runtime:` в промпте отправки задачи переопределяет значение по умолчанию из обёртки.

При переходе на маршрутизацию проекта переносите обёртки и конфигурацию вместе:

1. В каждом рантайме, который выбирает маршрут, замените каждую обёртку нативным файлом роли. В нативном файле роли есть ключи модели и уровня усилий.
2. Добавьте записи `roles` в `.specadoc.json`.
3. Запустите `role_routing.py` и проверьте результат.

Резолвер отклоняет целевой файл роли, если его обёртка указывает на другой рантайм: `wrapper points to <runtime>, not <runtime>; migrate to native roles`.

Старые планы могут содержать поля, которые Specadoc больше не использует. Это контрольная точка модели, снимки и отпечатки привязок и отказы от независимости для отдельных раундов. Такие планы всё равно проходят все гейты. Править их не нужно.

Установщик хоста может задать начальную маршрутизацию только через явную миграцию. Миграция должна сохранить существующий `root`, отклонить конфликтующие маршруты и изменённые управляемые роли и сохранить личные переопределения модели и уровня усилий. Она должна показать предпросмотр и восстановить каждый записанный файл, если применение не удалось. Для проекта с маршрутизацией миграция устанавливает нативные роли для каждого поддерживаемого рантайма.
