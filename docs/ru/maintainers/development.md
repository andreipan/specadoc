# Разработка

[English](../../en/maintainers/development.md)

Эта страница для участников, которые меняют сам Specadoc. Чтобы использовать
Specadoc в своём репозитории, начните с [карты документации](../index.md).
Версия, ZIP и шаги релиза описаны в разделе [Упаковка](packaging.md).

## Структура репозитория

| Путь | Содержимое | В релизном ZIP |
|---|---|---|
| `skills/specadoc/` | Скилл жизненного цикла: `SKILL.md`, `references/`, `scripts/`, `assets/` и `agents/openai.yaml` | да |
| `skills/tidy/`, `skills/codebase-design/`, `skills/domain-modeling/` | Сопутствующие скиллы | да |
| `skills/foreman/`, `skills/orchestrator/` | Управляющие скиллы с eval-кейсами в `evals/`. У orchestrator также есть `scripts/coordination_log.py` и `scripts/ba_register.py` | да |
| `agents/` | Адаптеры ролей для Claude Code. Их генерируют из переносимых контрактов ролей | нет |
| `scripts/` | Инструменты проверки и сборки для рабочей копии | нет |
| `tests/` | Модульные тесты и поведенческие eval-кейсы в `tests/evals/` | нет |
| `plugin.json` | Переносимый манифест плагина | да |
| `.claude-plugin/` | Манифест и маркетплейс Claude Code | нет |
| `.agents/plugins/marketplace.json` | Маркетплейс Codex для локального источника | нет |
| `docs/en/`, `docs/ru/` | Эта документация | да |
| `dist/` | Результат сборки. Git игнорирует эту папку | нет |

Инструменты в `scripts/`:

| Файл | Назначение |
|---|---|
| `check.sh` | Запускает все проверки рабочей копии. Запускайте его перед каждым коммитом |
| `render_roles.py` | Пишет `agents/*.md` по переносимым контрактам ролей. С `--check` только сравнивает |
| `claude-roles.json` | Frontmatter Claude Code для каждого сгенерированного адаптера |
| `package_plugin.py` | Проверяет пакет и собирает ZIP. См. [Упаковка](packaging.md) |
| `smoke_codex.py` | Офлайн-пилот Codex, который запускают только вручную. См. [Упаковка](packaging.md) |
| `docs_sync.py` | Сообщает о каждом английском документе без актуального русского перевода. С `--stamp` записывает хеш источника в русский документ |

## Версия Python

Скрипты используют только стандартную библиотеку Python. Действуют три
ограничения версии:

| Что | Минимум | Где задано ограничение |
|---|---|---|
| Скрипты скиллов в `skills/*/scripts/` | Python 3.10 | `specadoc_config.py` останавливается с ошибкой на более старом интерпретаторе |
| Реестры ролей Codex в TOML в `role_routing.py` | Python 3.11 | `tomllib` |
| `scripts/check.sh` | Python 3.11 | Тестам маршрутизации нужен `tomllib` |

Релизный ZIP не устанавливает Python. С Python 3.10 пользователь может
запускать скрипты жизненного цикла, но не определение ролей по реестру Codex.

## Запуск проверок

Запустите полную проверку из корня репозитория:

```bash
scripts/check.sh
```

Если `check.sh` выбирает не тот интерпретатор, укажите интерпретатор явно:

```bash
PYTHON=/path/to/python3.11 scripts/check.sh
```

Без `PYTHON` скрипт пробует `python3`, затем `python3.14` и далее вниз до
`python3.11`, затем `/opt/homebrew/bin/python3` и `/usr/local/bin/python3`.
Скрипт берёт первый интерпретатор версии 3.11 или новее. Если такого нет,
скрипт останавливается с сообщением `error: routing checks require Python 3.11+`.

`check.sh` выполняет эти шаги по порядку и останавливается на первой ошибке:

1. `scripts/render_roles.py --check`: адаптеры Claude Code совпадают с контрактами ролей.
2. `scripts/package_plugin.py --check`: манифесты, скиллы и содержимое ZIP корректны.
3. `python -m unittest discover -s tests -p 'test_*.py' -q`: все модульные тесты.
4. Если CLI `claude` есть в `PATH`, `claude plugin validate . --strict` и
   `claude plugin validate .claude-plugin/plugin.json --strict`.

Все шаги Python выполняются с `PYTHONDONTWRITEBYTECODE=1`.

Чтобы запустить один тестовый модуль, передайте имя его файла как шаблон:

```bash
python3 -m unittest discover -s tests -p 'test_validate_change.py' -q
```

## Модульные тесты

Все тесты используют `unittest`. Тесты работают во временных папках и не
запускают модель. Тест, который запускает CLI роли, ставит поддельный скрипт
`codex` или `opencode` первым в `PATH`.

| Группа | Файлы | Что проверяют |
|---|---|---|
| Скрипты жизненного цикла | `test_init_change.py`, `test_validate_change.py`, `test_specadoc_step.py`, `test_review_state.py`, `test_review_snapshot.py`, `test_final_run_and_status_json.py`, `test_task_brief.py`, `test_worker_scope.py`, `test_list_changes.py` | Создание изменения, гейты фаз, шаги apply, раунды ревью, область ревью и вывод статуса |
| Архив и корень артефактов | `test_archive_change.py`, `test_migrate_archive.py`, `test_migrate_root.py`, `test_specadoc_root.py`, `test_specadoc_doctor.py` | Архивные записи, миграции, определение корня и проверку состояния, которая только читает файлы |
| Сквозной тест | `test_lifecycle_cli.py` | Гейты CLI из пакета от спецификации до обычной архивации, с синтетическими одобрением и данными ревью |
| Роли и маршрутизация | `test_agents.py`, `test_role_routing.py`, `test_run_role.py` | Формат адаптеров, определение привязки роли и запуск ролей на другом рантайме |
| Учёт токенов | `test_collect_tokens.py` | Сборщик для транскриптов Claude Code, Codex и OpenCode |
| Текст скилла | `test_mode_budget.py`, `test_specadoc_explore.py`, `test_engineering_companions.py`, `test_management_skills.py`, `test_coordination_log.py`, `test_ba_register.py` | Лимиты размера, обязательные правила в тексте скилла, сопутствующие и управляющие скиллы и скрипты orchestrator |
| Пакет | `test_plugin_package.py` | Проверки манифестов, содержимое ZIP, воспроизводимую сборку и список eval-кейсов |
| Нейтральность | `test_neutrality.py` | Слова в публичном тексте, которые привязаны к хосту |
| Документация | `test_docs.py` | Состояние перевода, относительные ссылки, ссылки на другой язык и раздел справочника для каждого скрипта и режима |
| Регрессии после аудитов | `test_apply_reliability.py`, `test_apply_efficiency.py` | Сбои, которые нашли два аудита рабочего процесса |
| Регрессии после пилотов | `test_run<id>_regressions.py` | Сбои, которые нашли пилотные прогоны. См. следующий раздел |

`test_lifecycle_cli.py` тестирует механику артефактов. Он не доказывает
поведение модели или настоящий независимый PASS.

### Регрессионные тесты с именами пилотных прогонов

Многие исправления Specadoc появились после пилотных прогонов. В пилотном
прогоне Specadoc делает настоящие изменения в репозитории, а мейнтейнер потом
разбирает прогон. Каждый сбой из этого разбора получает регрессионный тест.

Тесты одного пилотного прогона или одной группы прогонов лежат в одном файле.
Имя файла содержит id прогона, например `test_run35_regressions.py` или
`test_run611_regressions.py`. Действуют такие правила:

- Docstring модуля называет прогоны, которые покрывает файл.
- Каждый тестовый класс покрывает один сбой. Его docstring описывает, что пошло не так в прогоне.
- Тест падает на старом поведении и проходит на исправлении.
- Тесты используют синтетические фикстуры. Многие файлы импортируют общий план и
  вспомогательные функции из `test_specadoc_step.py` и `test_apply_reliability.py`.

Если новый пилотный прогон показал сбой, добавьте тест в файл этого прогона.
Если у прогона нет файла, создайте новый файл по тому же шаблону имени.

### Тест нейтральности

`tests/test_neutrality.py` следит, чтобы в публичном тексте не было слов,
которые привязаны к хосту. В нём два теста:

- `test_skill_text_names_no_host_apps` читает `skills/**/*.md`. Тест отклоняет
  названия конкретных приложений-хостов и переменные окружения хостов.
- `test_no_host_specific_terms` читает файлы `.md`, `.py`, `.yaml`, `.json` и
  `.toml` в `skills/`, `agents/`, `scripts/` и `docs/`. Также тест читает
  `README.md`, `README.ru.md`, `CHANGELOG.md` и `CHANGELOG.ru.md`. Тест
  отклоняет названия личных инструментов, команды конкретного стека и пути
  частных проектов.

Шаблоны находятся в файле теста. Если тест упал, перепишите текст нейтральными
словами. Текст скилла называет возможность хоста, например «инструмент, который
понимает символы кода». Конкретные инструменты и команды хоста описывают в
инструкциях хоста или репозитория.

### Проверки документации

`tests/test_docs.py` проверяет документацию в `README.md`, `CHANGELOG.md` и
`docs/`, а также русские файлы каждого из них:

- Каждая относительная ссылка ведёт к существующему файлу.
- В первых шести строках каждого документа есть ссылка на документ на другом языке.
- В `docs/en/reference/scripts.md` есть раздел `## <name>.py` для каждого
  скрипта в `skills/specadoc/scripts/` и `skills/orchestrator/scripts/`.
- `README.md` и `docs/en/reference/modes.md` называют каждый режим из
  `skills/specadoc/SKILL.md`.
- У каждого английского документа есть русский документ по тому же пути, и
  русский документ актуален.

Первая строка каждого русского документа хранит SHA-256 его английского
источника: `<!-- source-sha256: <hex> -->`. Если английский документ
изменился, проверка сообщает, что русский документ устарел. Чтобы сделать его
актуальным, выполните шаги:

1. Обновите русский перевод.
2. Запустите `python3 scripts/docs_sync.py --stamp <russian file>`.

`python3 scripts/docs_sync.py` без параметров только сообщает о проблемах. Если
проблем нет, скрипт выводит `Documentation EN/RU: OK`.

## Переносимые контракты ролей и адаптеры

Источник — контракты ролей в `skills/specadoc/references/roles/`: `scout.md`,
`worker.md` и `reviewer.md`. Файлы `agents/scout.md`, `agents/worker.md` и
`agents/reviewer.md` — адаптеры Claude Code. `render_roles.py` собирает каждый
адаптер из трёх частей:

1. Frontmatter из записи роли в `scripts/claude-roles.json`.
2. Строка комментария о том, что файл сгенерирован.
3. Полный текст контракта роли.

Чтобы изменить роль, выполните шаги:

1. Отредактируйте контракт в `skills/specadoc/references/roles/`.
2. Если нужно изменить frontmatter для Claude Code, отредактируйте `scripts/claude-roles.json`.
3. Запустите `python3 scripts/render_roles.py`.
4. Закоммитьте контракт и сгенерированный адаптер вместе.

Не редактируйте `agents/*.md` вручную. Следующая генерация перезапишет правку,
а проверка упадёт ещё до неё.

`python3 scripts/render_roles.py --check` ничего не записывает. Если адаптера
нет или он отличается, команда выводит `Stale adapters: <paths>` и завершается
с кодом 1. `check.sh` запускает эту проверку первой. `test_plugin_package.py`
сравнивает адаптеры ещё раз.

В `claude-roles.json` одна запись на каждую роль, с ключами `name`,
`description`, `tools` и `model`. Эти значения действуют только для адаптеров
Claude Code. Модель Codex или OpenCode они не задают.

`tests/test_agents.py` проверяет каждый адаптер:

- Во frontmatter есть `name`, `description`, `tools` и `model`.
- В тексте ровно один блок между `<!-- specadoc:tooling:begin -->` и
  `<!-- specadoc:tooling:end -->`. В этом блоке нейтральные указания по инструментам.
- В тексте есть заголовки отчёта роли.
- Инструмент `Edit` или `Write` есть только у worker.

У orchestrator есть ещё один контракт,
`skills/orchestrator/references/roles/integration-verifier.md`. Сгенерированного
адаптера у него нет. `test_management_skills.py` проверяет его блок
инструментов и заголовки отчёта.

## Поведенческие eval-кейсы

Два набора eval-кейсов словами описывают ожидаемое поведение модели:

| Расположение | Формат | Содержимое |
|---|---|---|
| `tests/evals/specadoc.json` | Список кейсов с `id`, `request` и `expected_behavior` | 14 кейсов жизненного цикла, например прямой путь, повторное ревью после MINOR и недоступный reviewer |
| `tests/evals/tidy.json`, `codebase-design.json`, `domain-modeling.json` | `skill_name` и `evals`. У каждого eval есть `id`, `prompt`, `expected_output` и `files` | Кейсы для сопутствующих скиллов |
| `skills/foreman/evals/<case>/`, `skills/orchestrator/evals/<case>/` | `case.yaml`, `prompt.md` и `graders/*.md` | Кейсы симуляции с грейдерами по трассе: 3 для Foreman, 4 для Orchestrator |

В кейсе управляющего скилла `case.yaml` содержит `schema_version: "1.1"`, имя
кейса `name` и `expected_outcome`. Frontmatter файла `prompt.md` задаёт для
программы запуска eval-кейсов `max_turns`, `timeout_seconds` и `allowed_tools`.
Каждый грейдер начинается с `type: llm`, `focus: trace` и `weight: 1`.

Кейсы управляющих скиллов входят в релизный ZIP. Кейсы из `tests/evals/` не
входят.

Модульные тесты проверяют только наличие и формат этих кейсов:

- `test_plugin_package.py` сравнивает id кейсов в `tests/evals/specadoc.json`
  с утверждённым списком. Также тест проверяет, что у каждого кейса есть запрос
  и ожидаемое поведение.
- `test_management_skills.py` проверяет имена папок, поля `case.yaml`,
  frontmatter `prompt.md` и заголовки грейдеров.
- Файлы сопутствующих скиллов в `tests/evals/` не читает ни один тест.

В репозитории нет скрипта, который запускает эти кейсы с моделью. Успешный
`check.sh` не равен результату поведенческой оценки. Если вы запускаете кейсы с
моделью, запишите модель, хост и каждый результат. Каждый кейс, который не
запускался, запишите как пробел.

## Учёт токенов

Учёт токенов помогает сравнить стоимость изменения скилла между пилотными
прогонами. Полные правила — в
[measurement.md](../../../skills/specadoc/references/measurement.md). Скрипт —
`skills/specadoc/scripts/collect_tokens.py`.

Исполнение — один запуск: один транскрипт контроллера или один дочерний агент.
Сборщик читает каждый счётчик один раз, по его итоговому значению.
Возобновлённая сессия пишет новый транскрипт, поэтому это отдельное исполнение.

Сборщик выдаёт два итога:

| Итог | Содержимое |
|---|---|
| `unique` | Некешированный ввод, запись в кеш и вывод: новые токены, которые попали в транскрипт |
| `read` | Кешированный ввод: тот же контекст, который отправляется заново на каждом ходе. Этот итог больше зависит от числа ходов, чем от содержимого |

Собирайте все исполнения изменения, включая контроллер. Итог только по дочерним
агентам неполный. Запускайте сборщик один раз для каждого режима, например:

```bash
python3 skills/specadoc/scripts/collect_tokens.py <slug> --mode apply --harness claude <session.jsonl> --append
python3 skills/specadoc/scripts/collect_tokens.py <slug> --mode apply --harness codex <rollout.jsonl> --append
python3 skills/specadoc/scripts/collect_tokens.py <slug> --mode apply --harness opencode --directory <repo path> --session <controller-id> --append
```

- Если роль работала через `run_role.py`, добавьте её запись с флагом
  `--external-run runs/<name>.<role>.run.json`.
- С `--append` итоги попадают в `plan.md`, а строки для каждого исполнения — в
  `runs/tokens.md`.
- По умолчанию сбор предварительный. Используйте `--final` только для полного
  набора исполнений.

Учитывайте ограничения этих чисел:

- Не сравнивайте абсолютные числа между харнессами. У них разные правила кеша,
  модели и системные промпты. Указывайте харнесс рядом с каждым итогом.
- Итоги — это объём контекста из транскриптов, а не счёт провайдера. Не
  переводите их в деньги.
- В Codex `input_tokens` включает кешированный ввод. В транскриптах Claude Code
  эти два поля раздельные. Сборщик учитывает эту разницу.

### Бюджет контекста скилла

`test_mode_budget.py` ограничивает размер текста скилла, который загружает
режим. Лимиты заданы в `skills/specadoc/assets/mode-budget.json`:

- `SKILL.md` больше 5632 байт — ошибка.
- Файл в `references/` больше 15360 байт — ошибка.
- Если для режима `SKILL.md` вместе с файлами из `always` превышает `limit`
  режима, тест выводит предупреждение.
- Если справочный файл режима называет справочный файл, которого нет в
  манифесте, это расхождение. На расхождении тест падает.

Если справочный файл режима начинает называть новый справочный файл, добавьте
этот файл к режиму в `mode-budget.json`, в `always` или `conditional`.
